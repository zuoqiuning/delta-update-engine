# RFC 0001：多签名与密钥轮换

- 状态：Draft
- 目标版本：1.1.0
- 相关：[版本与兼容承诺](../reference/versioning.md)、[安全模型](../design/security.md)、[RFC 流程](README.md)

## 动机

当前清单只有一个 `.minisig`，信任集是配置里的 `signing_public_keys`。轮换密钥只有两种做法，都有缺口：

- 先发新版客户端加入新公钥，再换签名密钥：在“新版客户端尚未普及”的窗口里，旧客户端会因找不到可信密钥而更新失败。
- 双密钥并行下发（同一份清单签两次）：需要新的多签名表示法，否则发布侧只能覆盖 `.minisig`。

多签名让“旧密钥仍然可信、新密钥已被信任”的过渡期可被显式表达，而不是靠版本碰运气。

## 协议变更

- 主签名保持 `manifest.json.minisig`，语义不变：**旧客户端只读它**。
- 附加签名写到 `manifest.json.minisig.<key_id>`，`key_id` 是小写十六进制，取自 minisign 公钥的 key id。
- manifest 增加可选字段 `signing_key_ids: ["<id>", ...]`，列出本次发布的签名 key id；缺失表示“只有主签名”。
- 客户端：尝试主签名与所有 `signing_key_ids` 对应的附加签名，**任一通过即接受**，并把命中的 key id 记入日志与 `UpdateRecord`。
- 只有主签名存在而它由信任集之外的密钥签发时，行为与现在一致：`E_SIGNATURE_NO_TRUSTED_KEY`。

## 兼容性

| 场景 | 旧客户端 | 新客户端 |
| --- | --- | --- |
| 只发主签名（现状） | 正常 | 正常 |
| 主签名旧密钥 + 附加签名新密钥 | 正常（主签名在信任集内） | 正常（任一通过），记录命中 key id |
| 主签名新密钥 + 附加签名旧密钥 | 失败，直到客户端信任集包含新密钥 | 正常 |

结论：**主签名必须始终由“当前所有受支持客户端都信任的密钥”签发**。轮换完成前不得把主签名切到新密钥；这是发布纪律，不是客户端能自动弥补的。

## 迁移

1. 发布客户端：信任集加入新公钥（普通配置变更）。
2. 发布侧开始为每份清单写“旧密钥主签名 + 新密钥附加签名”。
3. 观察一个或多个版本窗口，确认客户端命中附加签名的比例接近 100%（`UpdateRecord` 的命中 key id）。
4. 把主签名切到新密钥，附加签名保留旧密钥一个窗口。
5. 从信任集移除旧公钥。

## 回滚

- 发布回滚：把清单与签名一起回滚到旧对象；附加签名的缺失不影响旧客户端。
- 客户端回滚：旧客户端只读主签名，因此第 4 步之前回滚是安全的；第 4 步之后回滚需要把主签名切回旧密钥。
- `.minisig.<key_id>` 是新增文件，删除它们不会破坏任何已发布客户端。

## 测试计划

先写 `crates/delta-update-engine/tests/security_contract.rs` 的用例，再实现：

1. 主签名有效、附加签名无效 → 接受，记录主 key id。
2. 主签名无效（key id 不匹配）、附加签名有效 → 接受，记录附加 key id。
3. 全部无效 → 拒绝，`E_SIGNATURE_NO_TRUSTED_KEY`。
4. manifest 声明了 `signing_key_ids` 但对应文件缺失 → 回退到主签名结果，不因缺文件而失败。
5. 旧格式（无 `signing_key_ids`、无附加文件）→ 行为与 1.0 完全相同。
6. 未知 `key_id` 的附加文件被忽略，不影响判定。

## 未决问题

- 附加签名的下载是并发还是按需：1.1.0 先按需，仅在主签名未命中时拉取，避免常态多一次请求。
- 是否需要发布侧 CLI 的 `--signing-key` 可重复传入：需要，但属于实现细节，不写进本 RFC 的契约。
