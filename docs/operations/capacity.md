# Delta Update Engine 性能基准与容量规划

> 本文为发布工程师与运维人员提供容量估算的定量依据。核心目标不是给出“某个算法跑得多快”，而是回答三个工程决策问题：**一次典型发布会产生多大的补丁和流量？运行侧需要多少磁盘和内存？发布者的 COS 成本在什么量级？** 所有基准数据标注来源，所有估算公式可代入实际参数。


## 1. 补丁体积基准

### 1.1 差分管线的压缩率区间

补丁体积是容量规划的起点。`delta-update-engine` 的差分管线由文件类型路由，不同管线有不同的压缩率量级：

| 管线                                   | 输入类型                          | 压缩率（补丁/目标）                 | 说明                                                         |
| -------------------------------------- | --------------------------------- | ----------------------------------- | ------------------------------------------------------------ |
| **Zucchini → bsdiff/HDiff → zstd**     | 自编译 PE（主 exe、自有 dll）     | **约 1%–3%**（归一化生效时）        | 归一化消除链接地址位移后，补丁可降一个数量级；效果强依赖编译器布局稳定性 |
| **bsdiff + zstd（默认管线）**          | 自编译 PE、第三方二进制           | **约 5%–15%**，取决于相似度         | 纯 Rust、可复现；没有归一化时的现实基线                      |
| **HDiffPatch + lzma2-9 / zstd-21-24**  | 大文件、相似度中等                | 约 6%–27%                           | 官方基准中的量级；作为可选加速器，需用真实样本复测           |
| **zstd 字典（`--patch-from`）**        | 高相似度文件                      | 约 7%–10%                           | 对文本/配置类文件效果好，patch 内存峰值较高                  |
| **全量（`strategy: full`）**           | 已压缩格式（png/jpg）或不相似数据 | 100%                                | 补丁 ≥ 全量 60% 时强制降级                                   |

**这些数字是量级，不是承诺**。最终体积由你的编译器版本、链接布局、sidecar 相似度决定；发布前必须用 `--dry-run --verbose` 跑一对真实版本，把实际比例代入容量模型。

**关键判断**：**主 exe 的补丁体积在启用 Zucchini 归一化时可到 1%–3%，默认管线通常在 5%–15%**。**sidecar 和资源文件的补丁占比取决于新旧相似度**——如果 sidecar 是第三方二进制且版本间变化较大，补丁可能达到全量的 20%–30%，此时 `--delta-max-ratio` 的 60% 降级阈值实际很少触发，但补丁体积本身需要被容量模型覆盖。

### 1.2 补丁生成与应用的性能开销

| 指标               | HDiffPatch + lzma2 | HDiffPatch + zstd | qbsdiff + zstd（默认）              |
| ------------------ | ------------------ | ----------------- | ----------------------------------- |
| **diff 速度**      | 约 5 MB/s          | 约 4 MB/s         | 待实测（纯 Rust，通常 2–10 MB/s）   |
| **patch 速度**     | 约 215 MB/s        | 约 935 MB/s       | 待实测（通常 100–500 MB/s）         |
| **patch 内存峰值** | 未公开             | 未公开            | old + new + diff 同时在内存，受预算约束 |

**数据来源与口径**：HDiffPatch 两列来自其官方基准的平均测速，仅代表可选加速器的量级。默认管线（qbsdiff + zstd）没有权威公开基准确认，**必须在项目第一天用自己的产物测**。

**构建侧含义**：一个 50 MB 的主 exe，用 lzma2 加速器做 diff 约需 10 秒；qbsdiff 可能更快或更慢，取决于块大小与文件相似度。在 CI 中并行生成多个候选补丁时，单文件耗时在秒级到十秒级，不会成为发布流水线的瓶颈。**运行侧含义**：patch 处理通常在几十到几百毫秒量级，实际耗时由下载主导，而非 apply。**内存才是硬约束**：bsdiff 类算法需要同时持有旧文件、新文件与差分流，务必用 `patch_memory_factor` 兜底。


## 2. 运行侧内存预算

### 2.1 分阶段内存峰值

| 阶段                      | 内存主要来源               | 量级                  | 可控性                                                       |
| ------------------------- | -------------------------- | --------------------- | ------------------------------------------------------------ |
| **Manifest 解析与比对**   | 清单 JSON + 文件哈希表     | **KB 到低 MB**        | 清单大小线性于文件数，1000 文件约 1–2 MB                     |
| **补丁下载**              | HTTP 缓冲区 + 临时文件写入 | **低 MB**             | 流式写入磁盘，不将整个补丁载入内存；≥ 8 MiB 的对象按 8 MiB 分块、4 路并发 Range，不支持 Range 时回退单流 |
| **补丁应用（apply）**     | 旧文件 + 补丁 + 新文件     | **文件大小的 1–3 倍** | 流式 apply 可约束在 1–2 倍；`E_PATCH_MEMORY_BUDGET` 在超限时拒绝 |
| **暂存区全树校验**        | 逐文件哈希，非同时载入     | **低 MB**             | 逐文件流式计算 SHA-256                                       |
| **Commit（rename/move）** | 文件句柄和路径             | **可忽略**            | 原子操作，不涉及文件内容复制                                 |
| **Journal 重放**          | 操作列表                   | **KB 到低十 MB**      | 每个 op 的路径字符串；上限 100 000 op / 32 MiB，重放时间与变化文件数线性。50 000 op 的编解码基准见 `benches/journal_verify.rs` |

**关键约束**：内存峰值的主要不确定性来自**单文件补丁应用**。对于 Tauri 应用，主 exe 通常在 **30–60 MB** 量级（NSIS 安装包约 71 MB，其中 Rust 二进制是大头）。如果 sidecar 较大（例如 **60–80 MB** 的 .NET runtime 或 **1.1–1.6 GB** 的 PyInstaller 打包产物），patch 内存预算需要按最大单文件尺寸设置。

**Journal 不是瓶颈**：release 构建下 50 000 个操作的编码约 15 ms、解码约 18 ms；重放耗时主要由逐文件 SHA-256 与文件系统操作决定，并与变化文件数线性。上限 100 000 op 覆盖了默认 `max_files = 20000` 的全部文件替换与大量删除。

**建议的默认内存预算**：`max_patch_file_size = 256 MB`，`patch_memory_factor = 2.5`。即单文件超过 256 MB 时走全量下载（避免大文件 patch 的内存风险），正常 patch 的内存上限约为 **640 MB**。这一预算覆盖绝大多数 Tauri 应用，包括带有中等规模 sidecar 的场景。对于 **1 GB 以上 sidecar** 的应用，需要在插件配置中显式提高 `max_patch_file_size`，或对该 sidecar 强制标记为 `full`。


## 3. 运行侧磁盘容量

### 3.1 磁盘占用构成

运行侧的磁盘占用由三部分组成，生命周期不同：

| 目录                                   | 内容                                       | 峰值时机              | 清理时机               |
| -------------------------------------- | ------------------------------------------ | --------------------- | ---------------------- |
| **根目录 R**                           | 已安装的官方文件                           | 稳定                  | 仅在 Commit 时被替换   |
| **暂存区 `staging/<version>/`**        | 只含变化/新增文件的目标版本                | prepare 完成后        | `confirm_healthy()` 后 |
| **Journal 目录**                       | write-ahead log                            | Commit 期间           | Commit 完成或回滚后    |
| **`.old` / `.trash/`**                 | 旧文件备份                                 | Commit 后到确认健康前 | `confirm_healthy()` 后 |

**峰值磁盘需求**出现在 **prepare 完成之后、Commit 执行之前**：

```
峰值需求 ≈ |R| + 变化文件总大小 + 临时余量
```

未变化文件**不复制、不硬链接**，只在 R 内原地校验，因此暂存区不会随安装体积线性增长。这也是跨卷安装不会被迫走硬链接的原因——硬链接本来就无法跨卷。

### 3.2 估算公式

```
峰值磁盘需求 ≈ |R| + 变化文件总大小 × 1.2 + 64 MB
```

64 MB 是 Journal、替换临时文件和文件系统元数据的宽松余量。`变化文件总大小 × 1.2` 覆盖了差分临时文件与目标文件同时存在的短暂窗口；跨卷替换时还需要在目标卷预留一份同等的临时空间。

**插件内置的 `staging_size_limit` 默认值为 2 GiB**。由于只物化变化文件，绝大多数发布远低于此；只有一次性替换数 GB 内容时才需要调高。磁盘不足时，prepare 会在下载前返回 `E_DISK_INSUFFICIENT`，而不是下载到一半才失败。


## 4. 网络传输与 COS 带宽

### 4.1 单次更新的下载量

单次更新的下载量由补丁体积决定：

```
下载量 ≈ Σ(每个 Modified 文件的补丁体积) + Σ(每个 Added 文件的完整体积)
```

**典型 Tauri 应用的量级**：

| 场景                         | 主 exe 补丁 | sidecar 补丁（若有变化）            | 资源文件 | 估算下载量            |
| ---------------------------- | ----------- | ----------------------------------- | -------- | --------------------- |
| 仅主 exe 小幅变更            | 80–500 KB   | 0                                   | 0        | **< 1 MB**            |
| 主 exe + 一个中等 sidecar    | 80–500 KB   | 6–20 MB（全量 20–80 MB 的 20%–30%） | 少量     | **6–20 MB**           |
| 主 exe + 大 sidecar 全量变更 | 80–500 KB   | 全量（sidecar 不相似）              | 少量     | **接近 sidecar 全量** |

**对比整包更新**：即使按保守的 10% 补丁比例，单次下载量也**至少降低一个数量级**。如果主 exe 是唯一变化文件，下载量从几十 MB 降至 **百 KB 级**。

### 4.2 COS 下行带宽约束

COS 不对单个请求的下载带宽施加严格上限，但存在存储桶级别的聚合带宽默认值（以下为量级参考，**配额与限速以云厂商当前文档和工单确认为准**）：

| 地域               | 单桶默认下行带宽                                             | 说明                               |
| ------------------ | ------------------------------------------------------------ | ---------------------------------- |
| 中国大陆公有云     | **10 Gbps**（公网上行+下行共享 15 Gbps 总量，达到阈值触发流控） | 单个存储桶的默认值，可通过工单提升 |
| 其他地域（如香港） | 约 5 Gbps                                                    | 同上                               |

**对增量更新场景的含义**：一个 **500 KB 的补丁**，在 10 Gbps 带宽下理论可支撑约 **2500 次/秒** 的并发下载。即使实际有效带宽只有 1 Gbps，也能支撑 **250 次/秒**。对于绝大多数单机软件发布者，COS 的默认带宽**远不是瓶颈**——瓶颈在客户端侧的网络条件。

### 4.3 预签名 URL 的有效期约束

预签名 URL 的有效期受**临时密钥寿命**和**URL 自身过期时间**共同约束，**以较短者为准**。临时密钥的最长时效为 **36 小时**，但 URL 本身通常应设置为**完成当前操作所需的最短期限**——过期后请求会中断，申请新签名后才能继续。

**对容量规划的含义**：预签名 URL 的有效期不应被用作“下载超时”的替代。一个 20 MB 的补丁在 2 Mbps 的慢速网络下需要约 **80 秒**；如果 URL 有效期设置为 15 分钟，足够覆盖绝大多数下载。**真正需要关注的是断点续传**——URL 过期后 Fetcher 刷新并续传，不会导致已下载字节丢失。


## 5. 分规模发布者的成本估算

以下估算基于 **500 KB 典型补丁**（主 exe 小幅变更）和 **10 MB 典型补丁**（含中等 sidecar 变化）两档，COS 标准存储下行流量单价按公开阶梯价格估算（实际单价以腾讯云账单为准，此处仅用于量级判断）。

| 发布规模                            | 月活跃更新次数 | 500 KB 补丁流量 | 10 MB 补丁流量 | 成本量级                             |
| ----------------------------------- | -------------- | --------------- | -------------- | ------------------------------------ |
| **小型**（1 万用户，月更新 1 次）   | 10,000         | 约 **5 GB**     | 约 **100 GB**  | 极低，通常处于免费额度或几元到几十元 |
| **中型**（10 万用户，月更新 2 次）  | 200,000        | 约 **100 GB**   | 约 **2 TB**    | 百元到千元级                         |
| **大型**（100 万用户，月更新 4 次） | 4,000,000      | 约 **2 TB**     | 约 **40 TB**   | 千元到万元级                         |

**关键判断**：增量更新的流量成本主要由**sidecar 或大文件的补丁体积**驱动，而非主 exe。主 exe 的 Zucchini 补丁在 **百 KB 级**，1 万次下载仅 5 GB。如果发布物的流量成本敏感，优化重点应放在 **sidecar 的差分管线**和 **`full_key` 回退的触发率**上——回退率每降低 1 个百分点，大文件场景的流量节省可能达到 GB 级。


## 6. 性能预算汇总表

| 指标                              | 预算值              | 依据                       | 超预算时的行为                 |
| --------------------------------- | ------------------- | -------------------------- | ------------------------------ |
| **单次典型下载量（主 exe 变更）** | 百 KB – 数 MB       | 归一化 1%–3%，默认 5%–15%  | —                              |
| **单次典型下载量（含 sidecar）**  | 6–20 MB             | sidecar 补丁 20%–30%       | `--require-delta` 在 CI 中阻塞 |
| **单文件 patch 内存峰值**         | ≤ 2.5 × 文件大小    | 预算系数                   | `E_PATCH_MEMORY_BUDGET`        |
| **单文件 patch 耗时（10 MB）**    | 50–500 ms           | 20–200 MB/s 有效处理速度   | 不构成瓶颈                     |
| **暂存区峰值磁盘**                | ≤ 变化文件总大小 × 1.2 | 只物化变化文件          | `E_DISK_INSUFFICIENT`          |

## 7. 容量规划的实操建议

**第一步：测量你自己的构建产物。** 用 `delta-update release --dry-run --verbose` 跑一对真实版本，记录每个文件的策略、全量大小、补丁大小和压缩比。基准表中的数字是通用量级，**你的 sidecar 和资源文件的实际相似度决定最终成本**。

**第二步：确定 `max_patch_file_size`。** 取你的构建产物中**最大单文件**的大小。如果它 ≤ 256 MB，默认预算通常够用。如果存在 1 GB 以上的 sidecar，**对该文件强制 `strategy: "full"`**，或提高 `max_patch_file_size` 并接受更高的内存峰值——大文件 patch 的内存风险由 `E_PATCH_MEMORY_BUDGET` 兜底。

**第三步：按用户规模估算流量。** 用 §5 的表格作为起点，代入你的实际补丁体积和月活跃更新次数。如果流量成本超出预期，优先检查 **sidecar 的补丁比例**和 **`full_key` 回退日志**——回退意味着客户端实际下载了全量，流量成本按全量计算。

**第四步：不要忽略构建侧的时间成本。** 默认管线的 diff 速度按 2–10 MB/s 估算，一个 100 MB 的 sidecar 单文件 diff 约需 **10–50 秒**。如果 CI 中并行生成多个候选补丁，总 diff 时间可能达到分钟级。对于文件数多的发布物，`--jobs` 的并行度应匹配 CI 的 CPU 核数。


**本文的核心判断**：增量更新的容量瓶颈**不在主 exe**——即使不启用归一化，主 exe 补丁通常也只是全量的个位数到十几个百分点，流量成本远低于整包。真正的成本变量是 **sidecar 和资源文件的补丁体积**，以及 **`full_key` 回退的触发率**。如果回退率高于预期，排查方向应该是“为什么差分失败”（本地源文件被修改、补丁策略选择不当、`delta-max-ratio` 阈值触发过早），而不是简单地增加带宽或磁盘。
