# Delta Update Engine 版本兼容与迁移策略

> 本文定义系统在时间维度上的兼容性契约。一个更新系统最危险的时刻，不是“更新失败”，而是**“更新成功后，老客户端再也无法接收任何后续更新”**。版本号不单调、密钥轮换留下信任缺口、schema 演进没有给旧客户端留退路——这些设计缺陷会在发布后数月才暴露，届时已安装的旧版本已经散落在用户机器上，修复成本远高于发布前想清楚。


## 1. 版本化模型：四个独立演进的维度

`delta-update-engine` 的兼容性不由单一版本号管理，而是四个正交的版本化对象，各自有独立的演进节奏和兼容性规则：

| 维度                | 载体                 | 演进触发条件              | 客户端行为               |
| ------------------- | -------------------- | ------------------------- | ------------------------ |
| **插件版本**        | Cargo crate + npm 包 | 命令、配置、公开 API 变更 | Cargo/npm 的 SemVer 解析 |
| **Manifest schema** | 清单 `schema` 字段   | 字段增删或语义变更        | 协议层显式拒绝或忽略     |
| **密钥集合**        | 客户端内嵌公钥       | 轮换、恢复                | 随二进制更新内嵌，无运行期写入 |
| **补丁策略标识**    | 清单 `strategy` 字段 | 新增差分管线              | 未知策略回退全量         |

**关键设计判断**：这四个维度**不共享版本号**。插件从 `0.1.0` 升级到 `0.2.0` 时，Manifest schema 可能仍然是 `1`；密钥轮换时，插件版本和 schema 都可以不变。将它们解耦，使每个维度的演进可以独立决策，避免“为了加一个命令而不得不升 schema”的连锁升级。


## 2. 插件版本的 SemVer 语义与双端同步

### 2.1 版本语义

插件遵循标准 SemVer `MAJOR.MINOR.PATCH`：

| 变更类型  | 版本递增                                              | 示例                              |
| --------- | ----------------------------------------------------- | --------------------------------- |
| **MAJOR** | 命令签名变更、配置字段删除、事件 payload 的破坏性变更 | 删除 `prepare` 命令，或改变其参数 |
| **MINOR** | 新增命令、新增可选配置字段、新增事件类型              | 增加 `cancel_prepare` 命令        |
| **PATCH** | Bug 修复、日志改进、内部重构                          | 修复断点续传的偏移计算            |

**已发布的命令语义永不改变**。如果需要改变 `check` 的返回结构，只能新增 `check_v2` 命令，保留 `check` 的旧行为直到下一个 MAJOR 版本。

### 2.2 Cargo 与 npm 的双端同步

Tauri 2 插件如果同时发布 Rust crate 和 npm 适配包，两者**必须保持完全相同的版本号**。官方插件的实践是：npm 包 `@tauri-apps/plugin-fs` 和 Cargo crate `tauri-plugin-fs` 的版本始终一致，补丁版本也可能引入协调变更。不匹配的版本可能导致运行时或构建错误。

Delta Update Engine 的 npm 包固定为 `tauri-plugin-delta-update-api`，与 Cargo crate 版本严格一致，发布脚本在同一次 CI 运行中同时提升两者。


## 3. Manifest schema 演进规则

### 3.1 兼容性矩阵

| 客户端支持的 `schema` | 清单的 `schema` | 客户端行为                                 |
| --------------------- | --------------- | ------------------------------------------ |
| `1`                   | `1`             | 正常处理                                   |
| `1`                   | `2`             | **拒绝**，返回 `E_MANIFEST_SCHEMA_TOO_NEW` |
| `2`                   | `1`             | 正常处理（向后兼容）                       |
| `2`                   | `2`             | 正常处理                                   |

**客户端只向后兼容，不向前兼容**。这是刻意的单向约束：旧客户端不应该被期望理解未来的 schema，拒绝是唯一安全的行为。

### 3.2 什么变更需要升 `schema`

| 变更                      | 是否升 schema            | 理由                                             |
| ------------------------- | ------------------------ | ------------------------------------------------ |
| 新增**可选**字段          | **否**                   | 旧客户端忽略未知字段即可                         |
| 新增**必填**字段          | **是**                   | 旧客户端因缺少必填字段无法正确解析               |
| 字段**语义变更**          | **是**                   | 即使字段名不变，旧客户端的处理逻辑已经错误       |
| 字段**删除**              | **是**                   | 旧客户端依赖该字段，删除会导致解析失败或行为异常 |
| `strategy` 枚举**新增值** | **否**（但客户端需回退） | 旧客户端遇到未知策略应回退全量或报错，而非猜测   |

**禁止复用旧字段名**。如果一个字段被废弃，应在下一个 schema 中移除，而不是赋予新语义。复用字段名是兼容性事故的常见来源。

### 3.3 `min_client_schema` 的发布侧约束

清单中的 `min_client_schema` 声明“使用此清单所需的最低客户端 schema”。发布侧必须遵守一条硬规则：**`min_client_schema` 不得高于任何仍可能存在的客户端所支持的 schema**。

crates.io 上有关 `minVersion` 的实践给出了清晰的教训：**永远不要把 minVersion 提升到应用商店尚未实际发布的版本；一旦这样做，所有仍在旧构建上的安装将被锁定，无法更新**。对 Delta Update Engine 而言，这意味着：

- 如果当前线上仍有 `schema: 1` 的客户端在检查更新，发布侧的 `min_client_schema` 必须保持为 `1`。
- 只有当确认所有活跃客户端都已升级到支持 `schema: 2` 的版本后，才能将 `min_client_schema` 提升到 `2`。
- “确认所有活跃客户端”在单机场景下不可精确做到，因此实践中应**至少保留一个完整的客户端版本迭代周期**，让旧版本有机会通过更新通道迁移。


## 4. 密钥轮换的迁移路径

### 4.1 从第一天交付一组密钥，而非一把

单密钥是系统性单点。如果客户端只内嵌一把公钥，私钥丢失或泄露意味着**所有已安装用户永久失去更新能力**——无法通过更新推送新公钥，因为新更新无法被旧密钥验证。这是**不可恢复的死更新路径**。

`delta-update-engine` 的信任锚是**一组 minisign 公钥**，验签条件是**任意一把受信公钥验证成功**即通过。这一设计直接来自业界实践：**从第一天就交付一组公钥，使得丢失或泄露的密钥可以被存活**——新公钥随客户端二进制更新内嵌，之后再用新密钥签名后续版本。

**信任集不可在运行期扩展**：客户端没有持久化信任集，也不接受清单携带新公钥。这是一个刻意的兼容性约束——可写信任集会被本地用户替换，从而把“能写应用数据”提升为“能向 machine-wide 安装目录写入任意代码”。

### 4.2 无信任缺口的轮换流程

```
阶段 1（稳定态）
  v1 内嵌：{ K1, K2 }
  发布签名者：K1

阶段 2（引入新密钥）
  v2 内嵌：{ K2, K3 }
  发布签名者：K1            ← 仍用旧密钥签名，v1/v2 客户端都信任

阶段 3（切换签名者）
  v3 起发布签名者：K2 或 K3  ← v2 客户端已内嵌这两把密钥

阶段 4（旧密钥退役）
  v4 起内嵌：{ K3, K4 }
  K1 私钥离线归档或销毁
```

**关键**：签名者切换发生在“新公钥已经被内嵌进客户端”之后，而不是同一份清单里既加公钥又换签名。旧客户端只信任 K1 时仍能接收 K1 签名的更新；它们升级到 v2 之后才信任 K3。**不存在信任缺口，也不依赖客户端持久化任何状态**。

### 4.3 轮换时“不留在原地”的约束

一个在密钥轮换中常见的错误是：轮换完成后，旧客户端因为仍然只信任旧密钥，而新版本只由新密钥签名，导致旧客户端**无法接收任何更新**，用户必须通过其他路径升级。

`delta-update-engine` 通过**两槽重叠 + 二进制内嵌**规避此问题：每个版本内嵌 `current + next`，签名者只使用**当前版本已内嵌**的密钥。旧客户端不认识 `release-3`，但它们认识 `release-2`，因此由 `release-2` 签名的更新对它们仍然有效。**轮换不依赖客户端先更新，也不依赖客户端持久化信任集**。


## 5. 补丁策略标识的前向兼容

`strategy` 是开放字符串，扩展**不升 schema**，但客户端必须遵守一条规则：**遇到未知策略时，如果条目提供了 `full_key`，回退到全量；否则该条目视为不可用，`check` 返回 `available: false` 并在 `detail` 中说明**。不把发布端的向前兼容问题变成用户侧的“更新失败”。

这意味着发布侧在引入新策略（例如未来的 `zucchini+zstd-v2`）时，必须同时为该条目的**旧客户端**提供 `full_key` 回退。发布 CLI 应默认对带补丁的条目生成 `full_key`，除非显式标记为“不提供全量回退”。这一约束使新策略的引入**不会让旧客户端失去更新能力**——最坏情况是旧客户端多下载一些字节，而不是更新失败。


## 6. 插件配置字段的迁移

### 6.1 新增可选字段

不升 `config_version`。旧配置文件缺少该字段时，插件使用安全默认值。Tauri 2 的配置解析在遇到未知字段时是否报错取决于 `#[serde(deny_unknown_fields)]` 的使用——**插件不应在 Config 结构体上启用 `deny_unknown_fields`**，以便未来新增字段时旧客户端可以忽略。


### 6.2 新增必填字段或字段语义变更

升 `config_version`，并在插件启动时检测旧版本配置：

```rust
if config.config_version < CURRENT_CONFIG_VERSION {
    return Err(Error::ConfigMigrationRequired {
        from: config.config_version,
        to: CURRENT_CONFIG_VERSION,
        message: "请按照迁移指南更新 tauri.conf.json 中的 delta-update 配置",
    });
}
```

**不在运行时自动迁移配置**。配置由开发者编写，自动迁移可能在开发者不知情的情况下改变行为。明确报错并要求开发者按迁移指南操作，是更安全的选择。

### 6.3 命令与事件的弃用

命令的弃用遵循“先标记、后移除”的两阶段：

1. **MINOR 版本**：命令标记 `#[deprecated]`，文档注明替代方案，命令仍然可用。
2. **下一个 MAJOR 版本**：命令移除。

事件 payload 的字段弃用同理：字段保留但文档标记弃用，下一个 MAJOR 版本移除。**不要在 MINOR 版本中删除事件字段**，即使它看起来“没有人使用”——前端代码的升级节奏不由插件控制。


## 7. 首次迁移：从无清单旧版本到协议版本 1

### 7.1 首次迁移的特殊性

一个已经存在的 Tauri 应用，在接入 Delta Update Engine 之前，没有清单、没有历史官方文件集合。首次更新时，客户端扫描本地安装目录，发现大量文件在远程清单中不存在。如果直接将这些文件归类为 `Removed` 并执行删除，**会误删用户数据**。

### 7.2 首次迁移的硬规则

- 客户端没有“历史官方文件集合”时，**所有本地存在但清单中不存在的文件被归类为 `Untracked`**。
- **不执行任何删除操作**。
- 仅执行 `Added` 和 `Modified` 的下载与替换。
- 首次 `confirm_healthy()` 后，将当前清单的文件集合写入历史官方集合，从此 `Removed` 判定生效。

这条规则保证：**第一次迁移不会误删用户数据**，哪怕用户把个人文件放在了安装目录里。


## 8. 回滚与降级发布的兼容性

### 8.1 正常发布与降级发布的区分

正常发布中，客户端拒绝 `version < 本地版本` 的清单（`E_VERSION_ROLLBACK`）；`version == 本地版本` 视为无更新，不报错。**降级发布必须通过 `rollback: true` 标志显式覆盖此守卫**，否则客户端不会接受。

### 8.2 降级发布的前向兼容约束

降级发布的清单必须满足：

- 签名由**当前受信密钥集合中的任意一把**生成（不能使用已退役的密钥）。
- 降级清单仍使用**当前 schema**（目前为 `1`）重新生成，而不是把历史版本的清单原样搬回来。`schema` 描述的是**协议格式**，不是应用版本；历史清单可能缺少当前客户端要求的字段，也可能带有旧的 `key_rotation` 之类已废弃字段。

### 8.3 回滚后立即重新发布的约束

回滚后，**不应立即重新发布被回滚的版本号**。原因：部分用户可能已经成功更新到该版本并调用了 `confirm_healthy()`，如果远程清单的 `version` 回退到旧版本，这些用户的客户端会拒绝降级（除非使用 `rollback: true`）。正确的做法是修复问题后发布**更高的版本号**。


## 9. 兼容性测试矩阵

每次发布前，以下组合必须被验证：

| 客户端版本        | 清单 schema               | 密钥集合            | 结果                                      |
| ----------------- | ------------------------- | ------------------- | ----------------------------------------- |
| 当前版本          | 当前 schema               | 当前密钥            | 正常更新                                  |
| 当前版本          | 当前 schema               | 密钥轮换中（旧+新） | 正常更新；新密钥只在二进制内嵌时生效      |
| 上一个 MINOR 版本 | 当前 schema               | 当前密钥            | 正常更新                                  |
| 上一个 MAJOR 版本 | 上一个 schema             | 当前密钥            | 正常更新（如果 `min_client_schema` 允许） |
| 上一个 MAJOR 版本 | 当前 schema（高于其支持） | 当前密钥            | 拒绝，`E_MANIFEST_SCHEMA_TOO_NEW`         |
| 任意版本          | 任何 schema               | 只有未被信任的密钥  | 拒绝，`E_SIGNATURE_NO_TRUSTED_KEY`        |


## 10. 设计总结

版本兼容与迁移策略的核心判断是：**兼容性不是“尽量不破坏”，而是“在协议层提供确定的退路”**。Manifest schema 的演进通过 `schema` 和 `min_client_schema` 给出双向的确定性；密钥轮换通过“从第一天交付一组密钥 + 两槽重叠”使单把密钥的丢失不成为永久死路径；补丁策略的扩展通过 `full_key` 回退使新算法引入不阻断旧客户端；首次迁移通过 `Untracked` 分类保护用户数据。

最容易被低估的两条规则是：**`min_client_schema` 不得高于线上仍存在的客户端所支持的 schema**，以及**密钥轮换不得依赖客户端先更新**。前者一旦违反，旧客户端被静默锁死；后者一旦违反，轮换本身成为更新通道的单点故障。这两条规则应在发布检查清单中作为硬门禁，而非事后补救。
