# Delta Update Engine 功能机制与模块设计文档

> 本文定义引擎的完整功能机制集合与模块级设计规格。判断标准不是“功能存在”，而是“在真实用户机器上，缺少它是否会导致不可接受的后果”。所有机制按 **engine（纯 Rust）→ plugin（Tauri 适配）→ cli（构建侧）** 三层归属，每个模块给出职责边界、关键设计决策和对外接口形态。

**依赖规则**：上层可依赖下层，**下层绝不反向依赖**。`Differ` 不知道 `Fetcher` 的存在；`Committer` 不知道 Tauri 的存在；`Crypto` 不知道 HTTP 的存在。这条规则使每个模块可以用最小化输入独立测试。


## 2. 各模块功能机制与设计规格

### 2.1 Manifest 模块——系统的唯一事实来源

**职责**：解析远程清单、生成本地清单、逐文件差异计算、版本单调性校验。

**功能机制列表**：

| 机制                                     | 设计规格                                                     |
| ---------------------------------------- | ------------------------------------------------------------ |
| **结构化清单解析**                       | 解析 `latest.json`，产出 `RemoteManifest { version, files: HashMap<RelPath, FileEntry> }`。`FileEntry` 包含 `sha256`、`size`、`strategy`、可选 `delta_key`/`delta_size`、`Added`/`Modified` 必填的 `full_key`、可选 `executable`。 |
| **本地清单生成**                         | 扫描根目录 R 下的所有文件，跳过引擎自建的临时目录与文件（`.old/`、`.trash/`、替换临时文件），计算 SHA-256，产出 `LocalManifest`。**不递归跟随符号链接**，防止扫描逃逸。 |
| **哈希缓存**                             | 扫描优先复用 `journal_dir/hash_cache.json` 中 `size + mtime` 匹配的 SHA-256，避免大目录重复 check 全量重哈希；更新确认后缓存失效。`prepare` 仍对未变化文件原地重哈希，缓存不会绕过内容校验。 |
| **逐文件差异分类**                       | 对每个远程条目与本地条目比对，产出四类结果：`Unchanged`、`Modified`（哈希不同且本地存在）、`Added`（本地不存在）、`Removed`（本地有但远程无）。**Added 直接走全量，不进入差分管线**。 |
| **版本与通道守卫**                       | 远程 `version` 高于本地才更新；等于本地视为无更新；低于本地仅在清单带签名保护的 `rollback: true` 时接受。通道不匹配视为无更新而非错误。**即使签名有效也执行该守卫**，这是协议层的防降级，不依赖签名完整性。 |
| **清单 schema 版本**                     | 清单包含 `schema: 1`。客户端遇到高于自身支持的 schema 时，返回明确错误而非静默失败，为未来协议演进留出协商空间。 |
| **排除列表（官方文件与用户数据的分界）** | 本地扫描和远程清单**共同**定义官方文件边界。远程清单中不存在的文件，本地扫描也不会将其纳入差异计算——**但“Removed”判定仅对曾经出现在任一历史清单中的文件生效**。历史集合持久化在 `journal_dir/known_files.json`，损坏或缺失时退化为“首次迁移”语义。这防止首次迁移时误删用户文件。 |
| **版本来源** | 本地版本取自**当前运行二进制的编译期版本**（`app.package_info().version`），不读取任何可写文件。磁盘上的版本标记只用于诊断与回滚，不作为信任或比较依据。 |

**关键设计决策**：清单解析与差异分类是**纯函数**；哈希缓存的读写只发生在 Engine 编排层。下载和磁盘写入分别由 Fetcher 和 Staging/Committer 承担。


### 2.2 Crypto 模块——签名、哈希、密钥信任链

**职责**：清单签名验证、补丁/全量对象哈希校验、公钥集合管理。

**功能机制列表**：

| 机制                           | 设计规格                                                     |
| ------------------------------ | ------------------------------------------------------------ |
| **minisign 清单验签**          | 对**原始清单字节**验证 detached `.minisig`，而非解析后的 JSON。签名字节与载荷字节必须一一对应，防止解析差异引入的攻击面。 |
| **信任公钥集合（非单密钥）**   | 二进制内嵌 **一组** 受信任的 minisign 公钥（`&[PublicKey]`）。签名验证通过的条件是：**任意一个受信公钥验证成功**。这是密钥轮换的结构性前提——从第一个版本就交付一组密钥，而不是一把。 |
| **密钥轮换语义**               | 每个客户端版本内嵌 `current + next`。轮换通过“由旧密钥签名、新版本内嵌新公钥”的更新完成；下一次发布即可用新密钥签名。**没有持久化信任集，也不接受清单携带新公钥**——可写信任集是一条本地提权路径。 |
| **补丁候选文件的“不可信”原则** | 差分应用产出的文件是**候选文件**，不是受信文件。只有 SHA-256 校验通过后，候选文件才被提升为“可进入暂存区的目标文件”。补丁是 untrusted input，哈希校验是唯一的信任建立点。 |
| **哈希算法选择**               | 文件级校验使用 SHA-256（与清单一致）。补丁对象内部的完整性校验可复用清单中的目标文件哈希，**不需要为补丁单独维护第二套哈希**——补丁应用后的目标哈希校验已经覆盖了补丁完整性。 |
| **验签时机**                   | 清单验签发生在 **prepare 阶段的最早期**，在下载任何补丁之前。补丁对象不单独签名——**容器头的源/目标哈希 + 应用后的目标哈希校验是不可省略的最终关卡**。未通过校验的字节永不进入根目录 R。 |

**接口形态**：实际实现是 `crypto::verify_manifest(raw_manifest, signature, keys)` 与 `crypto::validate_public_key`，**没有** `SignatureVerifier` trait。不要把未实现的 trait 写进公开 API 文档。


### 2.3 Differ 模块——补丁生成与应用的统一引擎

**职责**：构建侧生成补丁，运行侧应用补丁。**两端共用同一实现**，保证格式永不漂移。

**功能机制列表**：

| 机制                     | 设计规格                                                     |
| ------------------------ | ------------------------------------------------------------ |
| **策略路由（构建侧）**   | 当前只实现 qbsdiff+zstd；已压缩扩展名跳过差分。Zucchini/HDiffPatch/zstd 字典是未来规划，客户端没有 apply 实现。 |
| **差分引擎可插拔**       | **当前未实现 `DiffProvider`**；只支持 qbsdiff+zstd。未来引入 hdiff/zucchini 时再设计 provider 抽象，运行侧仍只按容器策略号分发。 |
| **参数矩阵**             | 当前 qbsdiff+zstd 使用固定 zstd level 3；`patch_memory_factor` 约束运行侧峰值。HDiffPatch/zstd-19/双候选是未来优化项，未实现。 |
| **双候选取小（构建侧）** | 未来规划：对每个文件生成多个候选并取最小；当前只生成一个 qbsdiff+zstd 候选。 |
| **补丁过大自动降级**     | 若候选补丁体积 ≥ 全量文件的 **60%**，直接标记该文件为全量传输，不生成差分补丁。差分不是目的，**流量最小化才是目的**；对已压缩或不相似的数据，全量可能更小。 |
| **补丁应用（运行侧）** | 当前实现一次性读入 source、patch 与解压 payload；`patch_memory_factor` 在 apply 前做预算检查，超限返回 `PatchError::MemoryBudget` 并回退全量。流式 apply 是后续优化项。 |

**策略标识协议**：清单条目包含 `strategy` 字符串（如 `"zucchini+zstd"`、`"qbsdiff+zstd"`、`"hdiff+lzma2"`、`"zstd-dict"`、`"full"`）。补丁容器头同时携带数值型 `strategy_id`。运行侧以容器头为准分发，清单字段用于规划与展示；两者不一致时回退全量并记录诊断，**不猜测策略**。

**补丁容器**：所有差分补丁统一封装为 `.tdp`，头部携带 magic、格式版本、策略号、压缩算法、目标大小、源哈希、目标哈希。运行侧在解压前即可拒绝不匹配的补丁；解压输出严格受目标大小约束，防解压炸弹。


### 2.4 Fetcher 模块——传输层的韧性

**职责**：清单获取、补丁/全量下载、断点续传、预签名 URL 刷新。

**功能机制列表**：

| 机制                    | 设计规格                                                     |
| ----------------------- | ------------------------------------------------------------ |
| **trait 抽象**          | `Fetcher` 是 trait，不绑定具体 HTTP 客户端。测试时可注入内存 fetcher，生产时使用 `reqwest` 或 `ureq` 实现。 |
| **断点续传**            | 下载目标为暂存区中的临时文件。中断后从临时文件的当前长度续传，使用 HTTP `Range` 头。服务端不支持 Range 时回退到全量重下，但**记录并告警**，不静默接受。 |
| **预签名 URL 自动刷新** | 下载中途收到 403/过期响应时，按协议文档 §9.5 向 `signing_endpoint` 换取新 URL，**从当前字节偏移续传**，不重新开始。刷新次数上限 3 次，防止循环。 |
| **下载即时校验**        | 每个对象下载完成后**立即**校验字节数与 `delta_size`/`size`；补丁再校验容器 magic/format/策略号/目标大小。失败丢弃临时文件并重试，重试上限 2 次。**损坏的补丁不进入 apply 阶段**。 |
| **资源上限**            | 清单 8 MiB、签名 64 KiB、单补丁 1 GiB、单全量 4 GiB；超限立即中止，不写入磁盘。 |
| **并发控制与限速**      | 同时下载的补丁数上限可配置（默认 4）。单文件下载速率可选限速，避免打满用户带宽或触发 COS 限流。 |
| **取消**                | `cancel_prepare` 通过取消令牌中止正在进行的下载；已写入的临时文件保留，供下次断点续传。 |
| **超时与重试分类**      | 连接超时、读取超时、5xx 错误可重试；4xx（除 403 过期外）不重试。重试使用指数退避，上限 3 次。 |

**接口形态**：
```rust
pub trait Fetcher {
    async fn fetch_manifest(&self) -> Result<Vec<u8>>;
    async fn fetch_signature(&self) -> Result<Vec<u8>>;
    async fn download(
        &self, key: &str, dest: &Path, resume_from: u64, max_bytes: u64,
    ) -> Result<DownloadReceipt>;
}
```


### 2.5 Staging 模块——两阶段提交的“准备”侧

**职责**：在暂存区物化变化文件，并对完整目标状态逐文件校验，产出 PREPARED 计划。

**功能机制列表**：

| 机制                      | 设计规格                                                     |
| ------------------------- | ------------------------------------------------------------ |
| **暂存目录隔离**          | 暂存区位于 `app_local_data_dir()/delta-update/staging/<version>/`，**不在根目录 R 内**。所有下载、差分应用、目标文件生成都在此完成。 |
| **只物化变化文件**        | 暂存区只存放 `Modified` 与 `Added` 文件的目标版本。未变化文件不复制、不硬链接，prepare 时在 R 内**原地校验**哈希。等价于“完整目标树已就绪”，但峰值磁盘从 `2×|R|` 降到 `|R| + 变化量`。 |
| **逐文件哈希校验**        | 暂存区的变化文件逐个校验 SHA-256；未变化文件在 R 内逐个校验 SHA-256。**任何一个文件不通过，整个 prepare 失败**，不进入部分提交状态。 |
| **磁盘空间预检**          | prepare 开始前估算所需空间：补丁临时文件 + 目标文件 + journal 备份预留。空间不足时在**下载前**返回 `Error::InsufficientDiskSpace`，而不是下载到一半才失败。暂存区与安装目录跨卷时，额外预留“复制到目标卷临时文件”的峰值。 |
| **PREPARED 计划的持久化** | 全部校验通过后，写入 `PREPARED` 计划（清单哈希、目标版本、每个变化文件的暂存路径与哈希、新版本文件全集）。下次启动时 `recover_and_cleanup()` 识别并**复用**，不重新下载；复用前重新校验暂存文件，发现篡改即丢弃。 |
| **暂存区大小上限**        | 可配置暂存区最大占用（默认 2 GiB）。超过上限时拒绝 prepare，防止单机磁盘被更新流程撑爆。 |
| **暂存目录不可在安装根内** | 配置校验阶段拒绝 `staging_dir` 位于 R 之内，避免更新素材被后续替换操作或清单扫描误伤。 |

**关键设计决策**：Staging **绝不直接写入根目录 R**。它只与暂存区和 Fetcher/Differ 交互。这是“不关软件”体验的物理隔离基础。


### 2.6 Journal 模块——使多文件替换成为原子操作

**职责**：写前日志（write-ahead log），使整个 Commit 过程具备崩溃原子性。

**功能机制列表**：

| 机制                                 | 设计规格                                                     |
| ------------------------------------ | ------------------------------------------------------------ |
| **写前协议（Write-Ahead Protocol）** | 在触碰**任何一个**根目录文件之前，Journal 先写入**完整的预期操作列表**并 flush。**flush 成功是提交点**。在提交点之前崩溃，根目录未被触碰；在提交点之后崩溃，恢复时重放 journal。 |
| **Journal 自身的原子性**             | Journal 文件本身通过“先写临时文件再原子 rename”的方式落盘，保证它“要么完整存在，要么完全不存在”，不存在撕裂的中间状态。 |
| **幂等重放**                         | `recover()` 重放 journal 时，**已经落地的操作视为 no-op**。同一份 journal 可以被安全重放多次而不产生副作用。这是崩溃恢复的核心性质：恢复过程本身可以被中断并再次恢复。 |
| **操作类型的最小集合**               | Journal 记录五类操作：`Backup(src → .old/)`、`Place(staging → R, sha256, size)`、`Trash(R/old → .trash/)`、`Restore(.old/.trash → R, sha256, size)`、`RemoveTrash`。每类操作自包含，不依赖其他操作的结果。 |
| **内容哈希绑定**                     | `Place` 与 `Restore` 必须携带目标 `sha256` 与 `size`。重放时先校验来源、再落地、再校验目标。**没有哈希的日志只能判断“目标是否存在”，无法阻止本地攻击者篡改暂存区后重算 checksum 注入任意字节**。 |
| **Journal 完整性校验**               | Journal 二进制格式带 magic header 与**尾部** checksum，覆盖 magic 到 payload 的全部字节（不含 checksum 自身）。校验失败的 journal **被拒绝并返回错误**，不尝试“尽力恢复”——损坏的 journal 重放可能导致比不恢复更糟的状态。 |
| **并发排他**                         | 暂存、提交、重放与回滚全程持有 `journal_dir/update.lock` 独占锁；第二个进程立即返回 `E_UPDATE_LOCKED`，不等待、不轮询。进程内再用异步互斥量串行化命令。 |
| **回滚也走日志**                     | 回滚生成一份“求逆”的 Journal（`Restore`/`Trash`），向前重放。这样回滚本身可被中断并再次恢复，且能正确还原 `.trash/` 中被删除的旧文件。 |
| **恢复方向：向前而非向后**           | 崩溃恢复**重放 journal 向前**（roll forward），将目录带到“已提交”状态，而不是回滚到之前。这与数据库 WAL 的语义一致：一旦 journal 的 commit point 已过，意图已经持久化，应当完成它。 |
| **保留旧的 journal 供诊断**          | 成功完成并清理后，journal 被删除。但如果在恢复过程中检测到异常，journal 被移动到诊断目录，供后续分析。 |

**设计参考**：数据库 WAL 与文件事务实现的通用语义是**“flush 即提交点”**与**“恢复向前幂等重放”**。本引擎采用相同语义，但操作粒度是文件级的 rename/backup/trash，而非任意文件写入。

**接口形态**：
```rust
pub struct CommitJournal { /* ... */ }

impl CommitJournal {
    pub fn begin(
        root: &Path,
        version: &str,
        commit_id: Uuid,
        ops: Vec<FileOp>,
        fs: &dyn FileSystem,
    ) -> Result<Self>;                       // flush = commit point
    pub fn mark_completed(self, fs: &dyn FileSystem) -> Result<()>;
    pub fn recover(root: &Path, fs: &dyn FileSystem) -> Result<JournalOutcome>;
}
```


### 2.7 Committer 模块——rename-then-replace 的执行者

**职责**：在 journal 的保护下，对根目录执行文件级替换。

**功能机制列表**：

| 机制                            | 设计规格                                                     |
| ------------------------------- | ------------------------------------------------------------ |
| **提交由替换进程执行**          | 主进程在应用退出前 spawn 同一已签名二进制的受限模式（`--delta-update-apply <journal_dir> <commit_id> [--relaunch]`），随后退出。替换进程不加载 WebView/Tauri，只读取 Journal 执行文件操作。主进程退出后才开始替换，保证运行中的 exe/dll 不阻塞 rename。 |
| **rename-then-replace 主路径**  | 对每个差异文件：旧文件先 rename 到 `R/.old/<commit_id>/<relpath>`（备份），暂存新文件 move 到目标相对路径。运行中的 exe/dll 已被进程映射，**rename 不破坏其内存映像**；下次启动加载新文件。 |
| **跨卷原子替换**                | 暂存区与安装目录不在同一卷时，move 退化为复制+删除。替换进程统一采用“在目标目录写临时文件 → 校验哈希 → 原子 rename 覆盖”，保证目标路径任何时刻要么是旧文件、要么是完整新文件。 |
| **软删除（Trash）而非物理删除** | 远程清单中不存在的旧官方文件，**不直接 `remove`**，移入 `R/.trash/<commit_id>/`。物理清理延迟到 `confirm_healthy()` 之后。这为回滚保留物理素材。 |
| **备份目录按 commit_id 隔离**   | 每次提交使用唯一 `commit_id` 子目录（`.old/<commit_id>/`、`.trash/<commit_id>/`），不会与上次残留或用户自建同名文件冲突，无需时间戳后缀。清理时按整个 `commit_id` 目录删除。 |
| **部分提交的防护**              | Commit 过程中任何一步返回错误，**不在内存中 unwind**（因为文件可能已被 rename）。错误被记录，控制权交给 `recover()` 或 `Rollback` 模块，由 journal 决定最终状态。**不会停留在“部分提交但无人知晓”的状态**。 |
| **提交后的状态标记**            | Commit 完成后，写入 `commit.status=completed`（包含版本与 `commit_id`）。Journal 与 `.old/.trash` 保留到 `confirm_healthy`，使崩溃循环可回滚；确认后统一清理。`recover_and_cleanup()` 据此知道下一步是“等待健康确认”、“继续完成”还是“回滚”。 |
| **权限适配层**                  | 写入 `Program Files` 需要提权。Committer 的 I/O 操作通过一个 `PrivilegedWriter` trait 执行。非提权场景使用普通文件操作；提权场景调用同一已签名二进制的受限 worker，在应用退出后完成写入。启动期恢复若需要写安装根，则用 `--delta-update-recover` 同步提权执行。**该差异对上层透明**。 |

**关键设计决策**：Committer **不决定“该不该替换”**。替换哪些文件、备份到何处，由 Manifest 差异结果和 Journal 的 ops 列表决定。Committer 只负责**在 journal 保护下执行**，保持职责单一。


### 2.8 Rollback 模块——崩溃循环保护与自愈

**职责**：检测“更新成功但新版本不可用”的场景，执行回滚。

**功能机制列表**：

| 机制                               | 设计规格                                                     |
| ---------------------------------- | ------------------------------------------------------------ |
| **启动尝试计数**                   | 每次应用启动最早期（`recover_and_cleanup()` 内），`attempts += 1`。**`confirm_healthy()` 调用时重置为 0**。计数持久化在应用数据目录，写入方式为“临时文件 + 原子 rename”。 |
| **崩溃循环阈值**                   | 默认阈值 **2**（可配置）。判定公式是 `attempts > threshold` 才回滚：第 1 次启动 `1`、第 2 次 `2`、第 3 次 `3 > 2` 触发回滚。阈值 `1` 表示第二次启动即回滚。**阈值不随更新重置**——持续崩溃的旧版本也应被检测。 |
| **回滚决策在 bootstrap 层**        | 回滚逻辑运行在 `setup` 的最早期，**早于任何业务代码和主窗口**。如果新版本主程序根本无法启动，业务代码中的回滚逻辑永远无法执行——**回滚必须是引导层的行为**。 |
| **回滚走 Journal**                 | 回滚不是简单的“把 `.old` 改回来”。它生成一份求逆的 Journal（`Restore` 备份、`Restore` `.trash` 中的旧文件、`Trash` 新版本新增的文件），向前重放，确保回滚过程可以被中断并恢复。 |
| **回滚后的版本标记**               | 回滚完成后记录 `skipped_version`。在该版本仍是远程最新版本时，自动检查不再自动 prepare 它；远程出现更高版本或 `rollback: true` 清单时清除标记。**不设时间窗口**——时间窗口会让用户在窗口结束后再次踩同一个崩溃版本。 |
| **`confirm_healthy()` 的时机语义** | 由前端在 UI 就绪后调用，或由 `auto_confirm` 在主窗口页面加载后延迟 `confirm_delay_ms`（默认 3000ms）自动调用。**调用即表示“应用已经进入可用状态”**；显式调用总是覆盖自动调用。`confirm_delay_ms = 0` 可关闭自动确认。 |

**回滚成功后的收尾**：`attempts` 重置为 0，写入 `skipped_version`，清除该版本的 PREPARED 计划与旧 Journal。**不重置 `attempts` 会让旧版本在下一次启动时再次触发空回滚**。

**状态机（Rollback 视角）**：

```
   Startup ──► attempt_count++
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
  count < threshold    count >= threshold
        │                   │
        ▼                   ▼
  正常启动，等待确认     执行回滚（经 Journal）
        │                   │
        ▼                   ▼
  confirm_healthy()     以旧版本启动
  → count = 0           → 标记“跳过该远程版本”
```


### 2.9 Path Resolver 模块——安装目录的可靠定位

**职责**：确定根目录 R，不依赖调用方的当前工作目录。

**功能机制列表**：

| 机制                      | 设计规格                                                     |
| ------------------------- | ------------------------------------------------------------ |
| **主路径：当前 exe 所在目录** | 通过 Tauri API 获取当前进程主模块路径，取其父目录并 canonicalize。**运行中的二进制位置是最权威的事实**，不依赖任何可被本地用户改写的注册表值。 |
| **显式覆盖**              | 便携版等特殊布局可通过 `install_dir` 配置覆盖；使用前校验它是绝对路径、存在、且当前 exe 位于其下，否则 `E_CONFIG_INVALID`。 |
| **注册表仅作诊断与回退**  | 读取 `HKCU\Software\<AppName>` 与 HKCU/HKLM 的 Uninstall `InstallLocation`，仅用于交叉校验与诊断。**即使注册表指向其他目录，也必须先验证当前 exe 位于该目录下**，否则忽略并记录告警——避免本地用户改写注册表把更新重定向到任意目录。 |
| **路径规范化**            | 所有路径在进入引擎前规范化为**小写 Windows 路径**（仅用于比对），但**实际文件操作保留原始大小写**。清单中的相对路径使用 `/` 分隔，引擎内部转换为平台分隔符；超过 260 字符时使用 `\\?\` 前缀。 |
| **拒绝逃逸**              | 任何清单相对路径在拼接后，必须验证其规范化结果仍位于根目录 R 之下。`..`、绝对路径、盘符、UNC、保留设备名、大小写冲突均被拒绝，返回 `Error::PathEscape` / `Error::PathInvalid` / `Error::PathCollision`。 |


### 2.10 State Machine 模块——可查询、可观测的内部状态

**职责**：暴露引擎的当前阶段，供插件层广播和前端展示。

**状态枚举**：

```
Idle
  ├── Checking
  ├── Downloading { total, completed }
  ├── Preparing { verified, total }
  ├── Prepared { version }                 ← “下次启动生效”
  ├── Cancelled { version }                ← 用户取消 prepare
  ├── Committing                           ← 仅替换进程可见
  ├── Committed { version }                ← 等待 confirm_healthy
  ├── RollingBack { to_version, reason }
  ├── RolledBack { to_version, reason }
  └── Failed { category, error }
```

**功能机制**：

| 机制               | 设计规格                                                     |
| ------------------ | ------------------------------------------------------------ |
| **状态变更事件**   | 每次状态迁移通过 callback 或 channel 发出。插件层将其转换为 Tauri event（`delta-update://state`）。 |
| **状态可查询命令** | `status` 命令返回当前状态快照。前端可以在任意时刻轮询或监听事件。 |
| **失败分类**       | `Failed` 携带协议文档 §7.3 的 `ErrorPayload`（含 `code`、`category`、`retryable`、`action`、`user_action`）。类别覆盖 `network`、`signature`、`manifest`、`security`、`disk`、`permission`、`patch`、`journal`、`rollback`、`config`、`platform`、`apply`、`internal`。**每一类对应不同的用户可读建议**，而不是统一的“更新失败”。 |


### 2.11 Error Taxonomy 模块——失败必须可诊断

**职责**：定义结构化错误类型，而不是用字符串或 anyhow 吞掉差异。

**关键错误类别与语义**：

| 类别              | 触发场景                     | 用户可操作建议                               |
| ----------------- | ---------------------------- | -------------------------------------------- |
| `Network`         | 下载中断、DNS 失败、超时     | 检查网络后重试                               |
| `Signature`       | 清单验签失败、公钥不匹配     | 联系软件提供商（可能是中间人攻击或密钥问题） |
| `DiskSpace`       | 暂存区或根目录空间不足       | 清理磁盘空间后重试                           |
| `Permission`      | 写入根目录被拒绝             | 允许替换进程的 UAC 授权；不要整体提权主进程   |
| `PatchMismatch`   | 补丁应用失败、目标哈希不匹配 | 全量回退已自动尝试；若仍失败，联系提供商     |
| `VersionRollback` | 远程版本低于当前版本且未授权降级 | 通常不需要操作；若持续出现，检查更新通道配置 |
| `PathEscape`      | 清单相对路径逃逸根目录       | 安全事件，不应发生；拒绝并记录               |
| `PathInvalid` / `PathCollision` | 路径结构违规或大小写冲突 | 发布端存在 bug；拒绝整份清单并上报           |
| `Manifest`        | 清单过大、版本非法、schema 过高 | 检查发布端配置；必要时升级客户端            |
| `Journal`         | 日志损坏、重放失败、更新被锁 | 收集日志与目录状态；不要手动删除 Journal     |
| `Rollback`        | 回滚自身失败                 | 最高严重级别，需要人工恢复备份               |
| `Config`          | 配置缺字段、非 HTTPS、版本过低 | 按错误提示修正 `tauri.conf.json`           |
| `Platform`        | 当前平台或安装形态不支持     | 改用受支持的安装形态或全量更新               |
| `Apply`           | 替换进程未能启动或异常退出   | 检查安全软件拦截；保留的暂存区可重试         |
| `Internal`        | 不应到达的分支               | 收集日志并报告                               |


### 2.12 插件层（tauri-plugin-delta-update）——生命周期编排与最小暴露面

**职责**：将引擎挂载到 Tauri 生命周期，暴露最窄的命令面和权限面。

**功能机制列表**：

| 机制                                        | 设计规格                                                     |
| ------------------------------------------- | ------------------------------------------------------------ |
| **Builder 注册与配置解析**                  | `Builder::<R, Config>::new("delta-update").setup(...).build()`。配置从 `tauri.conf.json` 的 `plugins.delta-update` 读取。必填字段：`config_version`、`endpoint`、`signing_public_keys`；常用可选字段：`auto_check`、`auto_apply`、`auto_confirm`、`channel`、`signing_endpoint`。 |
| **`setup` 最早期：`recover_and_cleanup()`** | 在插件 `setup` 中同步调用引擎的恢复入口。这一步**先于** auto_check，先于任何命令注册后的用户交互。它只做恢复：重放未完成 Journal、崩溃循环回滚、清理已确认健康的残留、复用 PREPARED 计划。**正常 Commit 不在这里发生**。 |
| **`auto_check` 后台准备**                   | `auto_check: true` 时，`setup` 中启动后台任务执行 `check_and_prepare()`。**不阻塞主线程**。准备完成时发出 `delta-update://state` 事件（`state = Prepared`）。 |
| **退出时应用更新**                          | `auto_apply: true` 时，插件监听 `RunEvent::Exit`，在退出前 spawn 替换进程；替换进程在应用完全退出后执行 Journal。`restart_to_apply` 命令走同一路径并额外拉起新版本。 |
| **自动健康确认**                            | `auto_confirm: true` 时，主窗口页面加载成功后延迟 `confirm_delay_ms` 调用一次 `confirm_healthy`，作为未写前端代码时的兜底。显式调用总是覆盖自动调用。 |
| **事件桥**                                  | 引擎状态机变更 → 单一 Tauri event `delta-update://state`。前端按 `state` 分支处理 `Prepared` / `RolledBack` / `Failed` 等。**事件只读，前端不参与决策**。 |
| **命令面（刻意窄）**                        | 暴露六个命令：`check`、`prepare`、`cancel_prepare`、`status`、`confirm_healthy`、`restart_to_apply`。**没有任何命令接收文件路径**，也没有“替换任意文件”的命令；`restart_to_apply` 只能消费已通过完整校验的 `Prepared` 状态。 |
| **默认权限包**                              | `permissions/default.toml` 包含六个命令的 `allow`。使用 `build.rs` 的 `tauri_plugin::Builder` 自动生成 `allow-<command>` 权限标识。**scope 不需要复杂定义**，因为这些命令不接收文件路径参数——路径由引擎内部从当前 exe 位置解析，前端无法传入任意路径。这从设计上消除了 scope 逃逸风险。 |
| **Extension Trait（可选）**                 | 为 `AppHandle` 提供 `.delta_updater()` 方法，返回可克隆的引擎状态句柄，供 Rust 侧其他插件查询状态。 |
| **平台显式拒绝**                            | 非桌面平台（含移动端）在注册期返回 `Error::UnsupportedPlatform`；macOS 签名 `.app` 包与 Linux `deb`/`rpm` 安装返回 `Error::UnsupportedFormat`。**在编译期或注册期明确拒绝**，而不是下载完才发现无法替换。 |

**权限设计的核心判断**：Tauri 2 的权限系统要求显式授予。本插件将暴露面收窄到**只读状态 + 触发检查/准备/取消 + 健康确认 + 重启已就绪的更新**。Commit 由替换进程在应用退出后执行，**没有“替换指定文件”的前端命令**。这意味着即使 WebView 被完全攻破，攻击者能做的上限是“反复触发 prepare、取消、或重启一个已通过全部校验的更新”，无法强制替换任意文件、无法读取根目录内容、无法绕过签名。


### 2.13 CLI 层（delta-update-cli）——构建侧的自动化管线

**职责**：一条命令完成“扫描产物 → 生成清单 → 生成补丁 → 签名 → 发布”。

**功能机制列表**：

| 机制                     | 设计规格                                                     |
| ------------------------ | ------------------------------------------------------------ |
| **目录树扫描与清单生成** | 扫描新版本输出目录，递归计算每个文件的 SHA-256 和大小，生成 `latest.json`。**自动排除**调试符号、`.pdb`、临时文件等发布时不应携带的产物（可通过 `.deltaignore` 配置），`--from` 目录使用同一套排除规则。 |
| **差分管线编排**         | 对 `from` 目录和 `to` 目录的每个**变化文件**生成 `.tdp` 容器（qbsdiff+zstd）。**未变化文件零补丁**。新增文件标记为 `full`。 |
| **补丁生成与降级**       | 并行生成 qbsdiff+zstd 补丁；≥ 全量 60% 时降级为全量。 |
| **签名**                 | 使用 minisign 私钥对**清单原始字节**签名，产出 `.minisig`。**私钥从临时文件路径或 CI secret 读取，不以内容形式出现在命令行**。 |
| **原子发布顺序**         | **先上传所有补丁和全量对象并 HEAD 校验，再上传签名，最后上传 `latest.json`**。客户端只有在清单指向某对象时才拉取，签名必须先于清单存在，否则会出现“清单 404”或“签名缺失”的窗口。 |
| **回滚发布**             | `--rollback` 生成版本号更低、`rollback: true` 的签名清单；客户端仅在本地版本更高时接受。 |
| **发布验证**             | 发布完成后执行 `verify`：从 COS 重新下载清单、验签、抽样下载补丁、应用并校验目标哈希；`doctor` 额外校验所有备用端点的版本一致性。 |

**当前实现范围**：补丁生成使用 qbsdiff+zstd 单管线；已压缩格式与超过 256 MiB 的文件直接走全量。Zucchini/HDiffPatch/ZstdDict 等策略标识已在协议中预留，作为后续增强接入。


## 3. 完整功能机制矩阵（按模块归属汇总）

| #    | 机制                           | 归属          | 缺失后果                             |
| ---- | ------------------------------ | ------------- | ------------------------------------ |
| 1    | 文件级清单 + 哈希比对          | Manifest      | 无法适配单/多文件，无法判断差异      |
| 2    | 版本单调性守卫                 | Manifest      | 可被降级攻击                         |
| 3    | 排除列表保护用户数据           | Manifest      | 首次迁移误删用户文件                 |
| 4    | minisign 多公钥验签            | Crypto        | 私钥丢失 = 永久失去更新能力          |
| 5    | 签名绑定原始字节               | Crypto        | 解析差异攻击面                       |
| 6    | 补丁候选不可信，哈希后信任     | Crypto        | 恶意补丁可写入根目录                 |
| 7    | 按文件类型路由差分策略         | Differ        | 对已压缩数据做无效差分，补丁反超全量 |
| 8    | Zucchini PE 归一化             | Differ        | PE 地址位移导致补丁膨胀数倍          |
| 9    | HDiffPatch + lzma2             | Differ        | 补丁体积非最优                       |
| 10   | 双候选取小 + 60% 降级          | Differ        | 理论最优不等于实际最优               |
| 11   | 流式 apply + 内存预算          | Differ        | 大文件 OOM                           |
| 12   | 断点续传                       | Fetcher       | 弱网环境下体验不可用                 |
| 13   | 预签名 URL 自动刷新            | Fetcher       | 下载中途 403 即失败                  |
| 14   | 下载即时校验                   | Fetcher       | 损坏补丁进入 apply                   |
| 15   | 暂存区隔离                     | Staging       | 下载过程污染根目录                   |
| 16   | 变化文件暂存 + 未变化文件原地校验 | Staging    | “重启生效”可能生效的是损坏文件       |
| 17   | PREPARED 缓存复用              | Staging       | 用户不重启则重复下载                 |
| 18   | 磁盘空间预检                   | Staging       | 下载到一半才失败                     |
| 19   | Write-Ahead Journal            | Journal       | 多文件替换崩溃后半更新               |
| 20   | 幂等向前重放                   | Journal       | 恢复过程自身不可靠                   |
| 21   | Journal 完整性校验             | Journal       | 损坏 journal 重放导致更糟状态        |
| 22   | rename-then-replace            | Committer     | 无法在不关软件的情况下替换运行中文件 |
| 23   | 软删除（Trash）                | Committer     | 回滚失去物理素材                     |
| 24   | 提权适配层                     | Committer     | Program Files 安装不可更新           |

## 4. 故障注入验证场景（设计验收标准）

一个模块的“完美”不体现在正常路径，而体现在以下场景中仍能给出**确定且可恢复**的结果：

| 注入点                                                | 期望行为                                                     |
| ----------------------------------------------------- | ------------------------------------------------------------ |
| 在 journal flush **之后**、第一个 rename 之前 kill -9 | 恢复时重放 journal，完成替换                                 |
| 在 journal flush **之前** kill -9                     | 根目录未被触碰，无操作                                       |
| 在替换第 3/5 个文件时断电                             | 恢复时从 journal 第 3 个操作继续，幂等跳过已完成的 1–2       |
| 补丁下载到 80% 时 URL 过期                            | 自动刷新并续传，不从头开始                                   |
| 补丁应用产出文件哈希不匹配                            | 回退到清单中的 `full` 对象重试，**不写入根目录**             |
| 新版本启动后 `confirm_healthy` 前崩溃两次             | 第三次启动触发回滚，以旧版本可用                             |
| 恶意清单路径为 `../../Windows/System32/x.dll`         | `PathEscape` 拒绝，不写入任何文件                            |
| 远程清单版本低于本地已安装版本                        | `VersionRollback` 拒绝，即使签名有效                         |
| 暂存区磁盘满                                          | `InsufficientDiskSpace`，在下载前返回                        |
| 写入 Program Files 被拒绝                             | `Permission`，提示以管理员运行或检查安全软件；**已暂存的 PREPARED 状态保留**，重试时复用 |
| 替换进程写完 Journal 后被 kill                        | 下次启动重放 Journal，目录到达确定的已提交状态或回滚态       |
| 篡改暂存区文件并重算 Journal checksum                 | 重放时来源哈希不匹配 → `E_JOURNAL_REPLAY_FAILED`，不写入任何字节 |
| 两个应用实例同时触发提交                              | 只有一个拿到 `update.lock`，另一个返回 `E_UPDATE_LOCKED`，不并发写入 |
| 暂存区在 D 盘、应用安装在 C 盘                        | 走“目标目录临时文件 + 原子 rename”，断电后目标文件完整       |
| 服务端返回 200 MB 清单                                | `E_MANIFEST_TOO_LARGE`，在解析前中止                         |
| 应用退出时用户取消 UAC                                | 保留 PREPARED 与暂存区，下次退出重试，不重新下载             |
| 替换进程启动新版本失败                                | 记录启动方式、PID 与退出码，返回 `E_APPLY_HELPER_FAILED`，旧版本仍可启动 |


## 5. 设计总结

这个引擎的“强大”不来自单一算法的先进性，而来自 **每一层都承担且只承担它该承担的责任**：Manifest 定义事实，Crypto 建立信任，Differ 压缩信息，Fetcher 保证传输韧性，Staging 隔离风险，Journal 赋予原子性，Committer 执行热替换，Rollback 提供自愈，Path Resolver 消除路径假设，State/Error 让一切可观测可诊断。**模块之间的边界越干净，每一个模块就越可以被独立推向生产级的严谨程度**。

下一步最值得投入的，不是继续增加机制，而是**先用故障注入测试把 2.6 Journal、2.7 Committer、2.8 Rollback 这三个模块的边界场景逐一验证到确定行为**。差分算法的优化可以借用成熟实现，但崩溃原子性和自愈语义只能通过验证来建立信心。
