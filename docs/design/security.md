# Delta Update Engine 安全威胁模型与密钥管理规范

> 本文定义系统的信任边界、威胁向量、防御机制和密钥生命周期。它不是架构文档的复述，而是对“攻击者能做什么、我们假设了什么、哪些防线是冗余的、哪些单点一旦失守就是系统性失效”的独立回答。安全审计应以本文为基准，发布流程应以本文的检查清单为闸门。


## 1. 安全定位与前提假设

### 1.1 本系统不解决什么

以下威胁**不在本系统的防御范围内**，必须在架构和运维层面承认：

| 不在范围内                        | 理由                                                         | 缓解手段（系统外）                                        |
| --------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------- |
| **WebView 内存破坏导致 RCE**      | Tauri 2 明确将 WebView 置于威胁模型之外，视为“弱链接”。WebView 与 Rust Core 共享进程地址空间，WebView 的 RCE 等价于 Rust Core 的 RCE。 | CSP、Isolation Pattern、及时更新宿主 WebView 运行时       |
| **操作系统级 rootkit / 内核后门** | 系统信任操作系统提供的隔离边界。                             | 端点安全产品、OS 更新                                     |
| **用户主动降级或侧载**            | 用户有权控制自己的机器。                                     | 不在技术层面阻止，但在协议层拒绝降级                      |
| **开发者私钥泄露后的持续滥用**    | 密钥一旦泄露，在轮换生效前，攻击者可以签发任意合法更新。     | 多密钥重叠、最小暴露面、泄露应急预案（见 §5）             |
| **COS 服务端自身被攻破**          | 云服务商的安全责任。                                         | 对象签名 + 客户端验签，使服务端被攻破也无法注入未签名内容 |

### 1.2 核心前提假设

系统的全部安全论证建立在以下假设之上：

1. **minisign/Ed25519 签名在计算上不可伪造**。只要私钥未泄露，攻击者无法构造通过验签的清单或对象。
2. **编译期内嵌的公钥集合是可信的**。二进制本身未被篡改。若二进制被替换，所有内嵌信任锚同时失效——这是**不可在系统内防御的前提**，依赖代码签名和分发渠道的完整性。
3. **文件系统的 rename 和 move 在语义上是原子的**（或至少不会产生撕裂的中间状态）。Journal 的原子性依赖于此。
4. **Tauri 的 capability 系统在运行时被强制执行**。插件暴露的命令面受 Runtime Authority 的 deny-by-default 策略约束，不因前端代码而改变。


## 2. 威胁建模

### 2.1 资产清单

| 资产                           | 位置             | 被攻破的后果                             |
| ------------------------------ | ---------------- | ---------------------------------------- |
| **签名私钥**                   | 离线 / CI secret | 攻击者可签发任意“合法”更新，全量用户沦陷 |
| **受信公钥集合（二进制内嵌）** | 客户端二进制     | 信任锚被替换，验签形同虚设               |
| **清单的版本与元数据**         | COS / 传输链路   | 降级攻击、指向恶意对象（若清单未签名）   |
| **补丁 / 全量对象字节**        | COS / 传输链路   | 注入恶意代码，但需通过哈希校验才能落地   |
| **安装目录 R**                 | 用户文件系统     | 任意代码执行、数据破坏                   |
| **Journal 与暂存区**           | 应用数据目录     | 操纵提交/回滚过程，制造半更新状态        |
| **WebView ↔ Rust Core 的 IPC** | 进程内           | 越权触发命令、路径逃逸                   |

### 2.2 攻击者画像

| 攻击者                  | 能力                                                | 主要目标                                     |
| ----------------------- | --------------------------------------------------- | -------------------------------------------- |
| **网络中间人（MITM）**  | 可拦截、修改、重放 COS 流量；可控制 DNS 或 CDN 节点 | 篡改清单指向旧版或恶意对象；注入损坏补丁     |
| **恶意 COS 对象持有者** | 可向桶内写入对象（若权限配置不当）                  | 用未签名的对象替换合法补丁                   |
| **本地低权限用户**      | 可在用户目录写文件，不可写 Program Files            | 篡改暂存区、伪造 Journal、耗尽磁盘           |
| **WebView 攻击者**      | 通过 XSS 或依赖链在 WebView 中执行 JS               | 调用插件命令，尝试路径逃逸或强制替换         |
| **供应链攻击者**        | 篡改构建产物或依赖                                  | 在签名前注入恶意代码，使签名“合法化”恶意内容 |

### 2.3 威胁向量与防御矩阵

#### 向量 A：清单篡改与降级攻击（最高优先级）

**更新器降级问题的教训**：不少更新器用 minisign 验证安装包，但**清单本身未被签名或认证**。攻击者修改未签名的 `version` 字段，指向一个仍然带有合法签名的旧版本，即可强制降级，无需私钥。这是**元数据与载荷信任不对称**的典型失效。

**本系统的防御**：

| 防御层                   | 机制                                                      | 效果                                                         |
| ------------------------ | --------------------------------------------------------- | ------------------------------------------------------------ |
| 签名覆盖原始清单字节     | 验签对象是 `raw_bytes(latest.json)`，不是解析后的 JSON    | 任何元数据修改（包括 `version`、`delta_key`、`sha256`）都会使签名失效 |
| 版本单调性守卫（协议层） | 拒绝 `version < 本地版本` 且未带 `rollback: true`；版本相等视为无更新。**与签名无关，独立执行** | 即使签名有效，未授权降级也被拒绝 |
| 先验签后解析             | 验证通过前不将字节交给 JSON 解析器                        | 消除解析器差异引入的攻击面                                   |
| `min_client_schema` 检查 | 拒绝客户端无法理解的新 schema                             | 防止未来协议被恶意降级到可攻击的子集                         |

**残余风险**：私钥泄露后的降级。多密钥与泄露应急预案只能缩短窗口，**无法在系统内撤销**已泄露私钥签名的更高版本（§5.4）。

#### 向量 B：补丁对象替换

**攻击路径**：MITM 或恶意桶写入者将 `delta_key` 指向的字节替换为恶意内容。

**防御**：

| 防御层       | 机制                                                         |
| ------------ | ------------------------------------------------------------ |
| 清单完整性   | `delta_key` 本身被清单签名保护，攻击者无法静默修改指向       |
| 目标哈希校验 | 补丁应用后，目标文件 SHA-256 必须与清单 `sha256` 一致。**补丁对象没有独立签名是刻意的**——目标哈希是更直接的语义正确性证明 |
| 全量回退     | 补丁校验失败时回退到 `full_key`，不重试损坏的补丁            |
| COS 传输层   | HTTPS + 对象 ETag 作为辅助完整性信号                         |

**关键判断**：补丁对象**不需要**独立签名。签名清单已经绑定了“期望的目标哈希”，而目标哈希校验是比“补丁字节哈希”更强的约束——它直接验证了语义结果。

#### 向量 C：路径逃逸

**攻击路径**：清单中的相对路径包含 `..`、绝对路径或 UNC 前缀，使替换操作写入安装目录之外。

**防御**：

- 协议层（§1.3）严格禁止 `..`、`.`、空段、绝对路径、盘符、UNC。
- 客户端做两层检查：清单解析阶段拒绝穿越段与 Windows 非法路径；journal 重放时对路径上的每一段检查符号链接 / junction / reparse point，拒绝把写入经由链接重定向到根目录之外。违反返回 `E_PATH_ESCAPE`/`E_JOURNAL_CORRUPT`，不写入任何文件。
- 路径字段在 Journal 中同样受此约束，重放时不信任 Journal 中的路径。

#### 向量 D：WebView 被攻破后的命令滥用

**攻击路径**：XSS 或恶意前端依赖获得 JS 执行权，调用插件命令。

**防御**（纵深）：

| 层                                  | 机制                                                         | 独立有效性                                         |
| ----------------------------------- | ------------------------------------------------------------ | -------------------------------------------------- |
| 命令面收窄                          | 只暴露 `check`、`prepare`、`cancel_prepare`、`status`、`confirm_healthy`、`restart_to_apply` 与诊断/历史/跳过命令（`export_diagnostics`、`open_diagnostics_folder`、`get_update_history`、`clear_skipped_version`、`skip_version`）。**没有指定文件的 commit 命令**。 | WebView 完全沦陷也无法写入 R                       |
| 路径不经过前端                      | 命令不接收任何文件路径参数。路径由引擎内部从当前 exe 位置解析。 | 消除路径注入                                       |
| 默认权限包最小化                    | `init` 默认写入 `manage-confirm`（11 个无路径参数命令的 `allow`，与兼容集 `default` 当前等价）；生产可用 `monitor` 进一步收窄。 | 即使 capability 文件被误配，可授予的集合本身是小的 |
| Isolation Pattern（建议开发者启用） | AES-GCM 保护的 iframe 拦截并改写 IPC payload。               | 增加 WebView 到 Core 的额外屏障                    |
| CSP 收紧                            | 禁止 `unsafe-inline`、限制 `connect-src`。                   | 降低 XSS 可达性                                    |

**攻击者上限**：反复触发 prepare（消耗带宽/磁盘）、读取状态信息。**无法强制替换文件、无法读取安装目录内容、无法绕过签名**。

#### 向量 E：Journal 篡改与恢复劫持

**攻击路径**：本地低权限用户篡改暂存区或 Journal 文件，使下次启动的恢复逻辑执行非预期操作。

**防御**：

- Journal 带 **magic + format + 尾部 SHA-256 checksum**，校验失败返回 `E_JOURNAL_CORRUPT`，**不尝试“尽力恢复”**。
- **checksum 不是认证**：本地攻击者可以重算。生产 worker 通过 `run_applier_from_context` 读取内嵌公钥，验证 `verified_manifest.json` 的 minisign 签名，并要求每个 `Place` 的目标哈希/大小出现在签名清单中；`commit.meta.json` 绑定 `commit_id`、`manifest_hash`、版本与 `install_root`。这样即使伪造 journal 和 checksum，也无法写入未签名内容。
- **验证与执行使用同一份内存 Journal**：`apply_commit_verified` 验签后直接把解码好的 `Journal` 交给 writer，不再按路径重新读取，消除了“验证 A、执行 B”的替换窗口。`Backup.dst` 必须精确等于 `.old/<commit_id>/<src>`，`Trash.trash_dst` 必须等于 `src`，否则拒绝执行。
- worker 还要求 `install_root` 精确等于自身可执行文件目录、路径拒绝 `.old`/`.trash`、staging/journal 在用户私有目录且不在安装根内。
- **迁移兼容**：旧的 `run_applier_from_args()` 不带 keys，调用时会失败关闭；新项目必须使用 `run_applier_from_context()` 或 `run_applier_with_keys`。引擎层的 `verify_commit_journal` 默认**失败关闭**：没有有效公钥就拒绝执行。`allow_unsigned_journal_recovery` 同时影响 `Engine` 的提交点与恢复路径（允许生成/执行无 `commit.meta.json` 的 journal），因此只用于测试/迁移；worker 入口永远传 `false`，插件的 `spawn_replacement` 会在组合该 flag 时直接返回 `E_CONFIG_INVALID`，避免“主进程已退出、worker 拒绝执行”的不一致现场。
- 提交、重放与回滚全程持有跨进程 `update.lock` 独占锁，第二个进程返回 `E_UPDATE_LOCKED`，不会并发改同一批文件。
- **残余风险**：本地攻击者可以删除 Journal 或暂存区，导致更新流程失败（可用性影响）；低层 `apply_commit` 是不验签的显式 legacy API，只能由测试/迁移工具调用。`run_applier`、`apply_commit_verified` 与恢复流程在无有效公钥时失败关闭。旧版签名清单的回放/降级仍受版本单调性约束，worker 不替代主进程的 `VersionRollback` 检查。

#### 向量 E2：清单/对象大小耗尽

**攻击路径**：MITM 或恶意服务端返回一份 200 MB 的清单、200 万个文件条目，或一个解压后 50 GB 的补丁，耗尽客户端内存与磁盘。

**防御**：

- 清单 8 MiB、条目 20 000、签名 64 KiB、单补丁 1 GiB、单全量 4 GiB 的硬上限，**在解析/写盘前生效**。
- 补丁解压输出严格等于清单 `size`，超出 1 字节立即中止（`E_PATCH_DECOMPRESSION_LIMIT`）。
- 路径长度、段数、保留设备名、大小写冲突在解析阶段拒绝。
- 这些上限不依赖发布端的正确性——签名只证明“发布者写了这些字段”，不证明字段本身合理。

#### 向量 F：供应链在签名前注入

**攻击路径**：构建环境或依赖被篡改，在签名之前将恶意代码编译进产物。

**防御**：

- 签名在 CI 中完成，私钥不落开发者本地。CI 的审批门和构建环境的隔离是**系统外控制**。
- 清单中的 `sha256` 在签名时确定，CI 产物在签名前经过完整性检查（见 §6 发布检查清单）。
- **本系统不防御构建环境本身的失陷**。这是发布管线的安全责任，由 CI 安全策略、审批流程和构建 reproducibility 覆盖。

#### 向量 G：COS 存储桶权限滥用与流量盗刷

**攻击路径**：桶策略过宽导致未授权写入或读取；预签名 URL 泄露后被第三方滥用，产生流量费用或分发未授权内容。

**防御**：

- **最小权限**：签名服务使用的密钥只允许对特定前缀执行 `GetObject`（下载清单/补丁）和必要的 `PutObject`（发布上传），**不授予整个桶的读写**。
- **临时密钥**：预签名 URL 使用临时密钥生成，遵循最小权限原则，权限范围严格限制在目标对象前缀。
- **短有效期**：预签名 URL 有效期设为分钟级，过期后由客户端自动刷新。泄露的 URL 窗口极短。
- **防盗链**：对清单和补丁对象启用 Referer 白名单或签名校验，防止第三方站点直接盗用流量。
- **分离发布与分发权限**：CI 使用的发布凭证与运行时签名服务使用的凭证是**不同的最小权限身份**。发布凭证可写，运行时凭证只读+生成预签名。


## 3. 信任边界

```
┌──────────────────────────────────────────────────────────────────┐
│  信任根：编译期内嵌的公钥集合                                     │
│  （若二进制被替换，一切失效——依赖代码签名与分发渠道）             │
└───────────────────────────────┬──────────────────────────────────┘
                                │ 验证
┌───────────────────────────────▼──────────────────────────────────┐
│  受信区域：通过验签的清单字节                                    │
│  · 清单中的 version、sha256、delta_key、full_key 被签名绑定       │
│  · 验签之后才解析 JSON                                           │
└───────────────────────────────┬──────────────────────────────────┘
                                │ 引用
┌───────────────────────────────▼──────────────────────────────────┐
│  待验证区域：补丁 / 全量对象字节                                  │
│  · 不可信输入。下载后不直接使用。                                 │
│  · 补丁应用产出候选文件 → 目标哈希校验 → 通过后才进入暂存区       │
└───────────────────────────────┬──────────────────────────────────┘
                                │ 校验通过
┌───────────────────────────────▼──────────────────────────────────┐
│  暂存区：已校验的变化文件 + 原地校验的未变化文件                  │
│  · 每个目标文件都已对照受信清单验证过哈希                         │
│  · Journal 只引用暂存区、.old/.trash 与根目录内的相对路径          │
└───────────────────────────────┬──────────────────────────────────┘
                                │ Commit
┌───────────────────────────────▼──────────────────────────────────┐
│  安装目录 R：仅通过 Journal 保护下的 rename/move 被修改           │
│  · 前端无任何命令可触达此区域                                     │
└──────────────────────────────────────────────────────────────────┘
```

**关键边界规则**：

1. **验签前的字节永远不解析**（防解析器攻击）。
2. **补丁对象在没有通过目标哈希校验前永远不进入暂存区**（补丁是不可信输入）。
3. **暂存区在没有完成全树校验前永远不进入 Commit**（防止部分正确的暂存树被提交）。
4. **安装目录 R 只被 Journal 保护下的原子操作修改**（前端和网络均不可直接触达）。
5. **Journal 在触碰 R 之前完成 flush**（write-ahead 语义是原子性的唯一保证）。

### 3.1 安装形态 × 信任根

**信任根 = 编译期内嵌；改 `tauri.conf.json` 必须重新构建才生效。** `signing_public_keys` 与 `pinned-keys` 的两个集合都在**构建期**决定：前者来自被编译进二进制的 `tauri.conf.json`，后者来自发布环境注入的 `DELTA_UPDATE_PINNED_PUBLIC_KEYS`。运行期没有任何可写的信任存储，所以“用户改了配置文件就能换公钥”并不成立。剩下两类风险是：**构建期**把错误的公钥编进正式客户端，以及**能写安装目录的人直接替换整个二进制**。

| 安装形态 | 配置来源 | 运行期可改写公钥 | 主要风险 | 建议 |
| --- | --- | --- | --- | --- |
| per-user（`%LocalAppData%`） | 内嵌 | 否 | 当前用户可替换 exe 与配置 | Authenticode 签名 + `pinned-keys` |
| per-machine（`%ProgramFiles%`） | 内嵌 | 否 | 需管理员权限才能替换 exe | Authenticode 签名；`pinned-keys` 可选 |
| 便携版（自定义目录） | 内嵌 | 否 | 目录可写，exe 与配置可被同权限进程替换 | Authenticode 签名 + `pinned-keys` |

`pinned-keys` 防的是“构建期配置被改”：发布环境另外注入一份公钥集合，客户端只信任**两者交集**。配置被 PR 篡改、分支带错密钥、或轮换只改了配置没改构建变量时，交集为空，应用拒绝启动（`E_CONFIG_INVALID`）而不是带着错误信任根运行。它**不防**二进制被替换——那属于代码签名与分发渠道，见 §1.2 前提 2。

宿主还可以在 `main` 开头调用 `set_trusted_keys(keys, mode)`，把进程信任根收窄到自己掌握的集合：`Intersect` 与内嵌配置取交集（为空则拒绝启动），`PinnedOnly` 用宿主集合替代内嵌集合（唯一可能放宽信任根的模式，由宿主承担该责任）。它必须早于 builder，因为替换 worker 在插件存在之前就要验 journal；晚调用会让 GUI 与 worker 拿到两个不同信任根，因此信任根一旦解析即冻结，迟到或重复调用返回 `E_CONFIG_INVALID`。

轮换顺序见 [版本与兼容承诺 §5](../reference/versioning.md#5-密钥轮换)：先发布 pinned 集合已包含新公钥的客户端构建，再用新密钥签名。

**`commit.meta.json` 与 `old_hashes.json` 的信任边界**：两者都是本地可写文件，**没有独立签名或 MAC**，因此不能作为独立信任根。`verify_commit_journal` 要求 `commit.meta.json` 存在，并重新验证 `verified_manifest.json` 的 minisign 签名；每个 `Place` 的 `dst/sha256/size` 必须出现在该签名清单中，`Backup.dst` 必须精确为 `.old/<commit_id>/<src>`。所以篡改 meta 或 `old_hashes` 不能把任意字节写进安装根，只能尝试改变“forward / rollback”的语义配对与回滚素材的选择。回滚 `Restore` 的哈希来自受签名清单绑定的 `installed_manifest.json` 或 `old_hashes`；前者是强约束，后者在本地被同时篡改时只能恢复“另一份曾经合法存在过的内容”，不能凭空写入新代码。这是有意接受的残余风险：跨进程 HMAC 需要传递密钥，得不偿失。

## 5. 密钥生命周期管理

### 5.1 核心设计原则：从第一天交付一组密钥，而非一把

**单密钥是系统性单点**：如果客户端只内嵌一把公钥，私钥丢失或泄露意味着**所有已安装用户永久失去更新能力**——无法通过更新推送新公钥，因为新更新无法被旧密钥验证。这是一个**不可恢复的死更新路径**。

**本系统的信任锚是一组 minisign 公钥**。验签条件是**任意一把受信公钥验证成功**即通过。这从结构上使轮换成为可能：一次更新可以由旧密钥签名，新版本二进制内嵌新公钥，下一次发布即可切换签名者。

**信任集不可在运行期扩展**。客户端没有持久化信任集，也不接受清单携带新公钥。原因很直接：可写的信任集是一条本地提权路径——能写应用数据目录的用户可以加入自己的公钥，再用自签清单把任意字节写进 machine-wide 安装目录。而它换来的收益是零：插件随应用二进制分发，新增公钥本来就可以通过一次正常更新完成。

### 5.2 密钥分层与职责分离

| 密钥槽位                 | 用途                | 私钥位置                           | 是否参与日常签名                  | 客户端信任                                |
| ------------------------ | ------------------- | ---------------------------------- | --------------------------------- | ----------------------------------------- |
| **release-1（current）** | 日常发布签名        | CI secret（加密）                  | 是                                | 始终信任                                  |
| **release-2（next）**    | 轮换备用 / 灾难恢复 | 密码管理器 + 离线（**绝不在 CI**） | 仅在轮换窗口或 release-1 不可用时 | 始终信任（从第一版内嵌）                  |
| **release-3（offline）** | 终极恢复            | 完全离线，永不接触联网机器         | 否，仅在灾难场景                  | 随下一个客户端二进制内嵌                  |

**三条硬规则**：

1. **release-2 必须从第一个发行版就内嵌**。如果等到需要轮换时才引入，旧客户端不会信任新密钥，轮换无法通过更新通道完成。
2. **release-2 的加密口令必须与 release-1 不同**。release-1 因 CI 自动化需要而暴露于 CI secret；release-2 的 purpose 就是“在 release-1 泄露时存活”，共享口令会使两者同时失效。
3. **口令必须是生成而非记忆的**（≥128 bits）。minisign 的 scrypt 参数（32 MiB, opslimit 2²⁰）只是离线攻击的适度刹车，不足以弥补弱口令。

### 5.3 无信任缺口的轮换流程

采用**两槽重叠 + 二进制内嵌**模型：每个版本内嵌 `current + next` 两把公钥，签名者只使用**当前版本已内嵌**的密钥。

```
阶段 1（稳定态）
  v1 内嵌：{ K1, K2 }
  发布签名者：K1

阶段 2（准备新密钥）
  v2 内嵌：{ K2, K3 }        ← 新增 K3，但不改变签名者
  发布签名者：K1              ← v1/v2 客户端都信任 K1

阶段 3（切换签名者）
  v3 起发布签名者：K2 或 K3   ← v2 客户端已内嵌 K2/K3
  旧客户端（只信任 K1）仍能验 K1 签名的更新，直到它们升级到 v2+

阶段 4（旧密钥退役）
  v4 起内嵌：{ K3, K4 }
  K1 私钥离线归档或销毁
```

**关键点**：

1. **新公钥只随二进制更新生效**，不依赖清单指令，不依赖客户端持久化任何状态。
2. **签名者切换发生在“新公钥已被内嵌”之后**，而不是同一份清单里既加公钥又换签名。
3. 旧客户端只信任 K1 时，仍能接收 K1 签名的更新；它们不会因为 K3 的出现而失去更新能力。
4. 攻击者无法通过篡改清单向信任集注入密钥——因为信任集根本不可写。

### 5.4 密钥丢失/泄露应急预案

| 场景                               | 影响                             | 响应                                                         |
| ---------------------------------- | -------------------------------- | ------------------------------------------------------------ |
| **release-1 私钥丢失（不可恢复）** | 无法发布 release-1 签名的更新    | 立即切换到 **release-2** 签名（该公钥已内嵌在所有客户端中）。发布一个由 release-2 签名、内嵌 release-3 的版本，进入阶段 3。**用户无感知，零信任缺口**。 |
| **release-1 私钥泄露**             | 攻击者可签发任意合法更新         | **系统内无法撤销**。立即用 release-2 发布更高版本的正常更新并加速推送；同时通过官网/应用商店/代码签名吊销等系统外渠道通告。攻击者同样能签更高版本，客户端无法区分——这是泄露场景的硬边界，不能靠“声明白名单”解决。 |
| **release-2 私钥丢失**             | 备用信任锚失效                   | 如果 release-1 仍安全，正常发布一个内嵌 release-3 的版本，把 next 槽位换成 release-3。如果 release-1 也已不可用，则只剩已内嵌的 release-3（若有）或需要用户手动重装。 |
| **所有内嵌密钥同时泄露**           | 信任根完全失效                   | **系统内无解**。必须通过软件分发渠道（官网、应用商店）发布带有全新公钥集合的版本，要求用户手动安装。这是“信任锚被替换”的不可防御场景。 |

### 5.5 私钥保管操作要求

| 要求                           | 具体措施                                                     |
| ------------------------------ | ------------------------------------------------------------ |
| **私钥不落仓库**               | `.key` 文件加入 `.gitignore`；CI 从 secret 解码到临时文件并只传文件路径，步骤结束立即删除 |
| **release-1 在 CI 中加密存储** | CI secret 加密，运行时解密到内存或临时文件，使用后立即删除   |
| **release-2 绝不在 CI**        | 仅存储在密码管理器和离线介质中，只在轮换窗口由授权人员手动使用 |
| **签名在 CI 中自动化**         | 每次发布由 CI 签名，而非开发者本地手动签名，保证签名日志可审计 |
| **公钥作为仓库变量**           | 公钥公开，作为构建变量注入，**不作为 secret**——它本来就是公开信息，不应被 secret 机制遮蔽 |


## 6. 发布安全检查清单

每次发布前逐项确认。**任何一项不通过，阻塞发布**。

### 6.1 产物完整性

- [ ] 清单中的每个 `sha256` 与 CI 构建输出逐文件一致
- [ ] 清单包含 `schema`、`version`、`min_client_schema`，且版本严格递增
- [ ] `full_key` 覆盖所有可能因差分失败而需要回退的文件
- [ ] `.deltaignore` 正确排除了调试符号、临时文件等不应进入清单的产物
- [ ] 若主 exe 配置了 Authenticode 签名，`Get-AuthenticodeSignature` 验证通过

### 6.2 签名

- [ ] `latest.json` 的 minisign 签名覆盖**原始字节**，验签通过
- [ ] 签名私钥未出现在日志、构建产物或仓库中
- [ ] 签名者与预期的密钥槽位一致（非轮换窗口应为 release-1）
- [ ] 若执行轮换，**新公钥已内嵌进本次发布的客户端二进制**，而不是只写在清单里
- [ ] 清单中不含 `key_rotation` 或任何运行期信任集指令

### 6.3 原子发布顺序

- [ ] **所有补丁对象和全量对象先上传**，并验证 COS 上存在且字节数正确
- [ ] 签名对象**先于**对应清单上传，`latest.json` 最后上传
- [ ] 上传后执行 dry-run：重新下载清单、验签、抽样下载补丁并校验目标哈希

### 6.4 COS 与密钥权限

- [ ] 运行时签名服务使用的密钥只有 `GetObject` 权限，范围限制在 `manifests/` 和 `artifacts/` 前缀
- [ ] 发布凭证与运行时凭证是不同身份
- [ ] 预签名 URL 有效期 ≤ 15 分钟，且每次刷新由服务端重新鉴权
- [ ] 防盗链配置已启用，非授权 Referer 被拒绝
- [ ] COS 访问日志已开启，异常下载量可告警

### 6.5 回滚素材

- [ ] 上一版本的清单和补丁仍然保留在 COS 的 `manifests/` 和 `artifacts/` 中
- [ ] 回滚清单携带 `rollback: true`、由受信私钥签名，且只对“本地版本更高”的客户端生效
- [ ] 回滚发布没有被误用为“重新发布旧版本号”；修复后必须用更高版本号发布


## 7. 安全设计总结

本系统的安全强度不来自任何单一机制的“强大”，而来自**信任链条上每一环都有独立可验证的约束**：

- **清单签名**使元数据不可篡改（消除了“只签制品、不签清单”的降级缺陷）。
- **版本单调性守卫**在签名之外独立拒绝降级，提供冗余。
- **目标哈希校验**使补丁字节的恶意替换无法落地，补丁被正确地视为不可信输入。
- **命令面收窄**使 WebView 沦陷不导致文件系统沦陷，前端没有任何路径触达 Commit。
- **多密钥信任集 + 二进制内嵌**使单把私钥的丢失不成为永久死路径，同时不存在可被本地篡改的信任存储。
- **Journal 的 write-ahead + 幂等重放**使替换过程在崩溃后仍可判定和恢复，篡改 Journal 不会使未校验字节进入安装目录。
- **COS 最小权限与临时密钥**使流量盗刷和未授权访问的窗口被压缩到分钟级。

**最需要审计关注的两点**：第一，**清单签名是否真正覆盖了所有决策字段**（版本、所有 `delta_key`、所有 `sha256`）——任何未被签名覆盖的字段都是降级或注入的入口。第二，**多密钥集合是否从第一个发行版就已内嵌**——如果等到需要轮换时才补，轮换将无法通过更新通道完成，单密钥的系统性风险将永久存在。
