# 崩溃循环分级设计

状态：已拍板并实现。采用方案 B + “正常退出减一”，**不引入 `acknowledge_start`**。
本文保留取舍记录，便于以后评估是否要放宽语义。

## 0. 决定

- `crash_loop_threshold` 默认值从 2 提高到 3。
- 新增 `exit_grace_period_secs`（默认 10 秒）：更新已提交但未确认时，正常退出且会话时长超过该窗口，`Engine::discount_clean_exit()` 把计数减一。
- `inspect` 显示 `启动尝试 / 崩溃循环阈值`，并在下一次启动就会回滚时输出警告。
- 不新增 `acknowledge_start` 命令。

理由：崩溃不会走 `RunEvent::Exit`，所以“正常退出减一”不会削弱真正的崩溃循环防护；而 `acknowledge_start` 会把“框架启动成功”和“业务健康”两个语义混在一起，并给前端一个廉价的重置计数的开关。

## 1. 现状

一次启动的计数发生在 `Engine::recover_and_cleanup` → `state::increment_attempts`。
计数只在三种情况下被清零：

1. 应用调用了 `confirm_healthy`（无论是否有 completed commit）。
2. 启动时既没有提交 Journal 也没有回滚 Journal（`recovery.rs` 的 `else` 分支）。
3. 回滚完成后 `confirm_healthy`/恢复路径清理 Journal。

当存在 `CommitStatus::Completed` 且 `attempts > crash_loop_threshold` 时，
`recovery::recover` 执行回滚并返回 `StartupOutcome::RolledBack`。
默认阈值是 2，也就是说：

- 第 1 次启动：`Committed`，界面正常。
- 第 2 次启动：仍 `Committed`（`2 > 2` 不成立）。
- 第 3 次启动：回滚到旧版本。

这段逻辑本身是自洽的，问题在于**它把所有“启动但未确认”都当成同一种信号**。

## 2. 被误伤的场景

“更新后打开看一眼就关掉”是完全正常的用户行为：

| 时间 | 行为 | 计数 |
| --- | --- | --- |
| 10:00 | 更新完成，用户打开应用看了一眼，关掉 | 启动 1 次，未确认 |
| 12:00 | 用户再打开，处理一件事，关掉 | 启动 2 次，未确认 |
| 15:00 | 用户再打开 | 第 3 次，触发回滚 |

代码本身没有崩溃，功能也正常，但因为应用没有调用 `confirm_healthy`，
用户第三次打开时会发现自己“退回旧版本”。这是支持工单的常见来源，
而不是理论风险。

反过来，如果应用在 `setup` 里立刻调用 `confirm_healthy`，
那么真正的崩溃循环（启动即 panic）也可能被提前清零——这就是当前模型的核心矛盾：
**同一个布尔信号既表示“框架起来了”，又表示“业务健康”。**

## 3. 三种启动的区分

| 分类 | 判定方式 | 可信度 | 建议计数 |
| --- | --- | --- | --- |
| crash-on-start | 进程在 `setup` 完成前退出或 panic | 高（进程没有走到确认点） | +1 |
| healthy-start-unconfirmed | `setup` 完成，N 秒内未调用 `confirm_healthy` 就正常退出 | 中（能启动，但业务未自检） | +1（当前行为） |
| acknowledged-start | 应用显式调用新增的 `acknowledge_start` | 高（只证明框架启动成功） | 0 或 -1 |

关键点：`crash-on-start` 和 `healthy-start-unconfirmed` 在磁盘上留下的痕迹几乎一样
（Journal 存在、没有确认、进程退出），引擎无法区分。因此分级不能靠“更聪明地推断”，
只能靠应用主动上报一个新的、语义更窄的信号。

## 4. 方案 A：新增 `acknowledge_start`

### 契约

```text
acknowledge_start() -> AckResult
```

- 只允许在 `setup` 成功返回后、主窗口创建前后调用。
- 语义：**框架启动完成**，不承诺业务初始化成功。
- 效果：把本次启动从“未确认”降级为“已确认框架启动”，计数不增加（或减 1）。
- 不清理 Journal、不删除备份、不改变 `confirm_healthy` 的语义。

### 风险

1. **降低检测严格性**：如果应用在调用 `acknowledge_start` 之后、业务初始化期间崩溃，
   崩溃只会反映在下一次启动的计数里，循环检测被推迟一轮。这是可接受的，因为
   真正的崩溃仍然会在下一轮累积。
2. **调用时机很难约束**：如果由前端调用，页面崩溃或脚本报错会导致信号丢失，
   比不调用更糟。因此必须由 Rust 侧在 `setup` 末尾调用，并在插件内记录一次性的
   “本进程已上报”标记，重复调用是幂等的。
3. **权限面扩大**：新增命令必须进入 `manage`（和 `prepare` 同级），
   不能默认暴露给只读的 `monitor` 集合。
4. **持久化**：需要一个 `acknowledged_at.json`（含 commit_id 与时间戳），
   并且必须绑定 `commit_id`，否则旧版本的 ack 会在新一次更新后错误地生效。

### 为什么先不实现

`acknowledge_start` 实际上把“健康确认”拆成了“框架确认”和“业务确认”两层，
而第二层仍然依赖应用自觉调用 `confirm_healthy`。如果应用不调用后者，
方案 A 只是把回滚从第 3 次启动推迟到第 4 次，并没有消除误伤。
收益取决于真实工单里“用户看到旧版本”的占比，目前没有数据支撑。

## 5. 方案 B：保持语义，提高默认值并让用户可见

不做新 API，只改两个可观测行为：

1. 把 `crash_loop_threshold` 的默认值从 2 提到 3。
   同样的“打开看一眼”行为需要 4 次启动才会回滚，覆盖一天内的正常使用。
2. `inspect` 的输出中显示本次启动的计数与阈值，例如：

   ```text
   启动尝试: 2（未确认启动；达到 3 次后回滚到 1.9.0）
   ```

   控制台用户在被回滚之前就能看到警告，而不是事后才发现。

代价：真正的崩溃循环会多经历一次失败启动才回滚。考虑到每次启动失败本身
不会破坏文件（Journal 仍在，回滚是幂等的），这个代价小于误伤正常用户。

## 6. 建议

短期采用方案 B：零 API 变更、零语义风险，且能被 `inspect` 立刻验证。
只有在真实工单证明“未确认启动”误伤率仍然偏高时，再引入方案 A；
届时 `acknowledge_start` 必须由 Rust 侧调用，并与 `commit_id` 绑定。

如果两者都做，推荐顺序是 B → 观察一个版本 → 再评估 A，
不要在同一个版本里同时改变默认阈值和计数语义。

## 7. 验收标准（实现方案 B 时）

- 默认配置下，连续 3 次“启动未确认”仍保持 `Committed`，第 4 次回滚。
- `crash_loop_threshold: 1` 时，第 2 次未确认启动即回滚。
- `confirm_healthy` 仍然在任何一次启动后立即清零计数。
- 回滚原因字符串包含实际次数，例如 `4 unconfirmed starts`。
- `inspect` 的 `attempts` 字段与回滚判断使用的是同一个计数。
- 既有测试 `lifecycle_contract`、`crash_harness`、`recovery` 全部通过。

## 8. 非目标

- 不区分“用户主动关闭”和“进程被任务管理器结束”。
- 不在本设计里引入遥测或上报。
- 不改变 Journal 的签名绑定、回滚顺序或 `StartupOutcome` 的变体。
