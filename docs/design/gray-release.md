# 灰度发布设计（仅设计，未实现）

本文讨论“只让一部分客户端拿到新版本”的方案。**当前引擎不实现灰度**：它涉及服务端分组与客户端身份，不是引擎单独能决定的。这里记录取舍，供接入方选择。

## 1. 问题

当前 `latest.json` 只有一个版本，所有客户端看到同一份清单。灰度需要回答三件事：

1. 客户端属于哪个组（谁拿到新版本）；
2. 服务端如何按组返回不同清单；
3. 从 5% 切到 100% 时，如何保证同一客户端不会来回跳。

引擎已有的能力：`config.headers` 允许给清单请求附加自定义 header；`channel` 让客户端只接受同通道清单。两者都不解决“分组”，只提供传输与过滤的钩子。

## 2. 方案 A：扩展 channel（`stable` / `beta` / `canary`）

发布者维护三份清单，客户端配置选一个 channel。

- 客户端改动：无（`channel` 已存在）。
- 服务端改动：无，按渠道上传不同的 `latest.json`。
- 切换方式：发布者把 canary 的改动逐批合并到 beta、stable，或直接把 stable 的 `latest.json` 指向 canary 已验证的版本。
- 优点：最简单，零新协议；崩溃回滚可直接复用 `rollback --to-version`。
- 缺点：分组是“整机”的，无法按比例自动扩大；用户可手动改配置加入 canary；发布者要维护多份清单，容易漏审计。
- 适用：小规模、愿意手动控制节奏的团队。

## 3. 方案 B：`client_id` + 服务端路由

客户端首次启动生成稳定随机 ID（存于 journal 目录），每次请求清单时带 `X-Client-Id`；服务端按 ID 哈希分桶，返回 stable 或 canary 清单。

- 客户端改动：生成并持久化 `client_id`；在 `config.headers` 中带上。
- 服务端改动：需要自建路由层（或用边缘函数），读取 header 并选择清单。
- 切换方式：调整分桶阈值（如 hash % 100 < 5 → canary），逐步放大。
- 优点：可按比例灰度、可随时缩量；分组稳定，不需要客户端参与决策；服务端可记录“谁拿到了哪个版本”。
- 缺点：引入服务端状态与隐私问题（ID 会出现在访问日志）；需要额外实现与运维；`client_id` 被伪造时只影响伪造者自己，但服务端不能把它当作身份认证。
- 适用：有服务端能力、需要精确比例的团队。

## 4. 方案 C：清单内 `rollout: { percent: 5 }`

客户端自己决定“我是不是这 5%”，例如用 `client_id` 的哈希对 100 取模。

- 客户端改动：需要 `client_id` 与稳定的哈希实现。
- 服务端改动：无。
- 优点：发布者只发一份清单，客户端自选。
- 缺点：客户端可被修改配置绕过；“百分比”依赖稳定 seed，否则每次检查结果不同；无法保证 5% 代表真实用户分布（离线、重装会漂移）；引擎要为此引入可选字段与哈希逻辑，收益不抵复杂度。
- 结论：**不推荐**。灰度是发布策略，应该在服务端或渠道层表达，而不是让客户端自选。

## 5. 对比

| 维度 | A：channel | B：client_id + 路由 | C：清单内 percent |
| --- | --- | --- | --- |
| 引擎改动 | 无 | 仅 `client_id` + header | 新字段 + 哈希 |
| 服务端改动 | 无 | 需要 | 无 |
| 精确按比例 | 否 | 是 | 名义上，可绕过 |
| 回滚成本 | 低（`rollback --to-version`） | 低（调阈值） | 低（改 percent） |
| 隐私影响 | 无 | 访问日志含稳定 ID | 同 B |
| 推荐度 | 近期可用 | 长期推荐 | 不推荐 |

## 6. 建议

- 近期：用方案 A。`channel` 与 `rollback --to-version` 已经能覆盖“先小范围试、出问题一键退回”的流程。
- 长期：方案 B。`client_id` 必须是**随机生成、仅本地持久化**，不采集设备指纹；服务端只做分桶，不把它当认证。
- 不实现方案 C。若未来确实需要，应先证明服务端路由不可行，并明确“客户端自选比例”的安全边界。

## 7. 待决问题

- `client_id` 存在 journal 目录还是应用数据目录？journal 可能在更新/回滚时被清理，需要独立位置。
- 灰度期间 `min_supported_version` 如何按组生效（canary 的清单不应把 stable 用户标记为必须更新）。
- 服务端如何避免“客户端先拿到 canary、缩量后又看到 stable”造成版本回落——需要 `rollback: true` 或更高的 stable 版本号。
